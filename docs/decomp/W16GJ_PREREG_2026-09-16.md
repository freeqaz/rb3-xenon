### H2 — REFUTED BY MY OWN PROBE. I predicted AT_LIMIT; it was a source construct.
I wrote H2 as "instruction scheduling ... if no source shape moves this cluster,
report AT_LIMIT". The FIRST probe moved it to 100.0%.

  Probe A: read the member through a local before the second Find:
      PanelDir *dir = mDir;
      RndTransAnim *boneanim = dir->Find<RndTransAnim>("bone_prog_bar.tnm", true);
  Result: ALL 417 instructions equal. report.json: fuzzy 100.0, mpn 100.0,
  masked_equal FALSE (so it is a genuine match, NOT alias/funclet forgiveness).

  Why it works: retail materialises the `mDir` reload into a scratch register
  immediately after the first Find returns, then `mr r3, r11`. That extra `mr`
  IS the entire 1,668-vs-1,664 byte delta. Reading the member through a named
  local reproduces the materialisation; using the member expression directly
  lets MSVC fold the load into r3 at the call site and the `mr` vanishes.

  ** THE DURABLE LESSON: I had already correctly established that the two
     sequences were semantically identical with an identical end state, and I
     concluded "pure scheduling => permuter territory". THAT INFERENCE WAS
     WRONG. Semantic identity of two instruction sequences does NOT imply the
     difference is schedule-only: here the difference was WHICH REGISTER THE
     VALUE WAS MATERIALISED INTO, which source CAN control (a named local
     forces materialisation; a member expression folded into the call site does
     not). "Identical multiset/end state => permuter" is a valid stopping rule
     only after the materialisation question has been asked.
  ** Corollary for the brief that sent me here: this row was labelled
     "regalloc-flavoured" and it was NOT. The one instrument that settled it was
     a single cheap SOURCE PROBE, not any amount of further charge analysis.
