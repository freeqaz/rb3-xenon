## What changed

| commit | what |

- **Retail bodies** (`tools/va_disasm.py`). Both read caps `+0xa` (`Gamepad.sThumbLY`, `lhz`)
  and mask it `rlwinm 0,0,27` (`& ~0xF`). 0x82529BA0 (0x1C bytes): `cmplwi 0x1730` -> 0x20
  (`kJoypadXboxMidiBoxKeyboard`), else 0x22 (`kJoypadXboxKeytar`). 0x82529DC8 (0x58 bytes):
  0x1530 -> 0x1f (`kJoypadXboxRealGuitar22Fret`); otherwise retail builds
  `is1430 || !is1530` into r10 and returns `r10 ? 0x1e : 2` (`subfic/subfe/rlwinm 27..29/addi 2`).
  r10 is always 1 on that path, so the `2` arm is dead and every other value is 0x1e
  (`kJoypadXboxButtonGuitar`). Unlike SetupHXGuitar/Drums, neither stores to JoypadData
  (r3 is dead in both). The native bodies say exactly this.
- **Stubs.** The two `peripheral-only` stubs were dropped only by rerunning
  `tools/rb3_app_link_stubs_gen.py` as its docstring says: the `.s` was emptied, rb3-app linked
  (`--error-limit=0`, 157 undefined) and the generator was fed that log. Modulo `.Lname_N`
  renumbering, the result is the old file minus exactly the two stubs, their name strings and
  the now-unused `peripheral-only` ring string. It also corrects the header, which said
  157 functions while the file held 155 (gemwalk's hand edit removed two blocks and did not
  update the count); it now says and holds 153. The generator's RULES comment says that the
  `peripheral-only` rule now matches nothing.
- `RB3_APP_EXTRA_PADS` accepts the two new kinds through the same table (`KindToSubType`).
- No `src/` file changed: nothing for `tools/ab_measure.py` to price (the match build compiles
  no `native/`), and no ODR/selftest run here (left to the coordinator, as briefed).

## Findings

### 1. The keytar needs nothing beyond its setup body

Prediction: keys would follow the guitar walk unchanged. **Right.** `keys` resolves to
`kJoypadXboxKeytar` (34), manual calibration, `walk.txt` (verbatim `a25/walk.txt`) reaches
`game_screen` with `p0 track 4` (kTrackKeys). Song 1: 268/268 hit, 0 miss, score 36,451,
5.0 stars, crowd 1.0, energy 1.0; song 2 (stats reset at frame 10,022): 152/152, 19,127,
5.0 stars. `deploy` stays 0 (autoplay does not deploy, as on guitar/drums).
`ReadSingleXinputJoypad`'s keytar arm reads `TheKeyboard` (null natively: no USB MIDI keyboard),
which its `TheKeyboard ? ... : false` guard handles.

### 2. The button pro guitar cannot calibrate natively (retail behaviour; walk uses the 22-fret)

First cut: `proguitar` = subtype 25 with `sThumbLY` 0 -> `kJoypadXboxButtonGuitar`.
Prediction: manual calibration as on guitar. **Wrong** (walk dg, bin-k1): `cal_welcome` went to
`cal_audio_screen` (automatic), then `cal_manual_failed_screen`, and looped. Cause, retail:
`JoypadIsCalbertGuitar` is true for the button guitar, and `JoypadGetCalbertValue` reads its
sensor from raw pro-guitar report bytes 10/11, which `ReadSingleJoypad` zeroes natively (no HID
report). That is the right result for a dead sensor, not a port bug. Fix: `proguitar` reports
caps `sThumbLY` 0x1530 -> `kJoypadXboxRealGuitar22Fret` (31), not a Calbert guitar; controller
`hx_midi_guitar_xbox`; calibration is then the manual screens (walk dg2, bin-k2).

### 3. The pro guitar's first-boot route goes through the campaign

With the 22-fret, `hint_goalcomplete_screen` exits to `meta_loading_campaign_screen` ->
`accomplishment_screen` instead of the main hub (keys and guitar go to `main_hub_screen`, then
`hint_rb3_welcome_screen`). It takes the second `a` to leave the hint (the first, at +30, does
not), and three `b` (cancel, action 2 for `hx_midi_guitar_xbox`) to leave
`accomplishment_screen` for `main_hub_screen`. With two `b` it stays (pinned by det-record
diff: xb and the first GA are identical through frame 576, and xb's transition at frame 577
follows its third `b` at poll 575). The new input log line showed every press resolving
to the expected action (a -> 1 confirm, b -> 2 cancel, start -> 4, down -> 7), so this is screen
flow, not pad mapping. The screens are data (the ark's dtbs do not grep as text), so I did not
establish why the pro instrument is routed to the campaign. `walk_pg2.txt` is `walk.txt` with
those presses inserted.

### 4. Open: `trainers_guitar_tutorial_01_screen` bounces back immediately

Off the song path, from the campaign the walk's `a` presses entered
`trainers_guitar_tutorial_01_screen`, and it exited back to `accomplishment_screen` one frame
after entering (frames 4145 -> 4146 and 4235 -> 4236 in dg2, the second time with no press
anywhere near). Later attempts showed `accomplishments_wrong_instrument_screen`, so this may be
the game rejecting a 5-lane guitar goal for a pro guitar. That is plausible retail, but not
checked against retail. Not chased.
