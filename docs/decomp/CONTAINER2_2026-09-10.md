## 1. The briefed realisable figure was 3.1× too small, and the criterion was wrong

The brief priced the prize as "41 of those rows (19,792 B) also sit in the
≤3-mismatch band". Two problems:

* **Band membership is not the crossing criterion.** `matched_code` is
  all-or-nothing per row, so a row crosses only if **every** charged site on it
  resolves. A row with 3 mismatches of which 1 is a container site does not
  cross when the pair is fixed; a row with 8 mismatches all of which are
  container sites does.
* Measured with the census's own instrument (`container_type_census.diff_one`,
  `--analyze`, graded ruler), the fully-covered population is
  **311 rows / 61,952 B**, of which 240 rows / 38,640 B have a single mismatch.

Intermediate wrong numbers are recorded because they show the failure mode: a
first pass keyed on `crossing_worklist.classify_arms`' relocation extraction
returned **0 fully-covered rows** — a decisive-looking negative produced by a
join bug (the mismatch table's Target column carries the opcode text, `bl ?…`,
which `container_type_census.symbol_in()` strips downstream and my join did
not). The rewrite carries an explicit anti-vacuity assertion: if no site joins,
it exits rather than reporting an empty result.

## 3. What settles these, and what each instrument cannot do

Three map-independent channels were used. Each is stated with its failure mode,
because a channel that cannot fail is not evidence.

1. **Node-allocation size.** `sizeof(_List_node<T>) = 8 + sizeof(T)`, emitted as
   a literal `li r3, N` in the node creator. A pointer element MUST give 12.
   *Failure mode:* it cannot distinguish types of equal size — which is not a
   defect but the finding itself (§7).
2. **Template-forced caller.** A free or static function whose own mangled name
   carries the container as its only parameter cannot reach a sibling
   instantiation's body. *Failure mode:* unsound for a MEMBER function, which
   may operate on a member container rather than its parameter — `Hookup@CharHair
   (ObjPtrList<CharCollide>&)` is a live example, so member callers were used
   only as corroboration, never as proof.
3. **Dtor vtable → `??_R4` COL → `??_R0` type name** (the instrument the
   coordinator proposed). `ObjRefConcrete<T>::~ObjRefConcrete` stores a per-T
   vptr, emitted as a `lis`+`addi` pair into `.rdata`. *Failure mode named in
   advance: a folded vtable would make two dtors load one address.* It does not
   fire here — all 70 resolved dtors load **distinct** addresses resolving to
   **distinct** classes, which is the built-in control, and it is also the
   mechanical reason the family did not fold.

Channels 2 and 3 were cross-checked on six addresses and **agree 6/6**. That
matters because channel 2 reads caller names *from the map*, i.e. it is
potentially circular; channel 3 reads retail's own RTTI strings and is not.

## 6. Instrument error rate — the census's NOFOLD label

The census's `NOFOLD` is defined as "both names appear in the address-keyed map
at DIFFERENT addresses ⇒ they did not fold". It is sound **only if the map's
name at each address is right**, and the docstring says so. This lane measured
that premise:

| family | map names checked | provably wrong | rate |
|---|---:|---:|---:|
| `~ObjRefConcrete<T>` (vtable/RTTI) | 70 | 30 | **43%** |
| `list<T*>::insert` (node size) | 8 | 6 | **75%** |

So `NOFOLD` inherits a 43–75% error rate on exactly the addresses it consults.
The headline pair demonstrates it: `list<CharClip*>::insert` vs
`list<Object*>::insert` was labelled NOFOLD because the two names sit at
`0x823d14c0` and `0x823c3ac8` — but `0x823c3ac8` is not `list<Object*>::insert`
at all (its node is 24 B and it copy-constructs a `CharIKHand::IKTarget`), so
the NOFOLD premise rested on a wrong name. The truth is the opposite of the
label: **the pointer-element family DID fold.**

⇒ **`NOFOLD` should be read as "not refuted by the map", never as "did not
fold".** It is one-directional in the direction the docstring documents, and
additionally noisy in proportion to map error.

`CALLER_ORDINARY` produced no false positive, but it conflates two sub-cases its
own rationale treats as one. The docstring justifies the label by "the element
type is chosen by a DECLARATION … a wrong header declaration is representable".
For the largest sub-population here — `PollDeps` overrides taking
`list<Object*>&` — the type is fixed by **the overridden virtual's signature**,
so our source *cannot* be wrong and SOURCE_WRONG was never available. Splitting
CALLER_ORDINARY on "container comes from a parameter of an overriding virtual"
vs "container is a member declaration" would make the candidate class smaller
and truer.

## 7. Why `list<int>` calls `list<CharClip*>::insert` (coordinator's question)

Asked explicitly: does retail's insert body carry a `StlNodeAlloc<CharClip*>`
relocation, which would make `list<int>` callers impossible without an allocator
fold? **The relocation does not exist.** The body at `0x823d14c0` has exactly
ONE relocation — a `bl` to the node creator — and the allocator is inlined into
that creator, whose only external call is `MemOrPoolAlloc` after `li r3, 12`.
The chain bottoms out at an **untyped 12-byte allocation**. Since
`sizeof(int) == sizeof(T*) == 4`, `list<int>` and every `list<T*>` compile to
relocation-identical code and `/OPT:ICF` folds them into one body. Corroborated
without any fold model by T-INCONS: the creator's own map name spells
`Dep@CharPollableSorter*` while the insert's spells `CharClip*`.

⇒ MasterAudio's `list<int>` site is a **genuine fold**, irreducible for source
work. The map rename does not close it and was never expected to — which is why
the measured `+38` is below the naive site count.

## 9. The mangling defect, because it generalises

One of the 30 generated dtor names was wrong: for `T == ObjectDir` the second
template argument repeats an earlier name, so MSVC emits the **back-reference**
`??1?$ObjRefConcrete@VObjectDir@@V1@@@UAA@XZ`, not the expanded
`…@VObjectDir@@VObjectDir@@@@…`. **0 compiled objects define the expanded form;
35 define the back-ref one.** The address was therefore renamed to a name
nothing emits: the row un-paired and the 1,512 B pair it was meant to close
stayed open.

⇒ **GENERATING a mangled name is not OBSERVING one.** Any map repair that
constructs a name must check the exact spelling against our own objs' symbol
tables *before* measuring. Two further consequences, both measured:

* The repair needed a **chain**, because the back-ref name was already in use at
  `0x82395650` — and a precondition `assert` is the only reason a duplicate did
  not land. `0x82395650`'s vtable independently resolves to
  `ObjPtr<CharCollide>`, agreeing with the forced-caller channel for the 7th
  time (7/7).
* **A name-shaped filter silently under-selects compressed manglings.** My
  vtable sweep's regex required the expanded tail, so every back-ref-spelled
  instantiation was invisible to it — which is why `0x82395650` was never a
  candidate. The sweep reported "76 mapped dtors" and the true population is
  larger.
