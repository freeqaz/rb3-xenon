# BP4 lane dossier — songmgr (2026-06-11, read-only recon @ main 78a6ee6, baseline 7785)

## Verdict (one line)

All 9 SongMgr near-misses share **one systemic root cause — SongMgr class-shape
divergence** (head −0x10, per-TU map 0x18→0x1c, primary-vtable own-slot prefix
0x54→0x38 and −1 slot); **none** is an independent 1-instruction source fix.
GO as a single gated layout-reconstruction lever (rb3-Wii oracle confirmed:
`../rb3/src/system/meta/SongMgr.h` declares `SongMgr : public MsgSource, public
ContentMgr::Callback`; our header has DC3-era `Hmx::Object` base +
`AlternateSongDir` extra virtual), expected +9 with reveal upside; **decision
gate first** (retail vtable dump) because the exact base composition is not yet
proven (see §5 tension).

## 2. Derived retail vs ours layout (two-equation proof)

With layout X = offsetof(mAvailableSongs), set = 0x18, map = M:
`mState = X + 0x18 + M` and `mSongCache = X + 0x18 + 5M + 8`.

- Ours: mState 0x5c, mSongCache 0xc4 → **M = 0x18, X = 0x2c** (consistent:
  Hmx::Object 0x28 + Callback 4; Object = vptr 0, TypeProps-inline 0x4,
  mTypeDef 0x10, mNote 0x14, mName 0x18, mDir 0x1c, mRefs 0x20 → 0x28, per
  `src/system/obj/Object.h`).
- Retail: mState 0x50, mSongCache 0xc8 → **M = 0x1c, X = 0x1c** (over-determined,
  both equations agree; also mCachedSongMetadata @0x54 measured directly).

| member | retail | ours |
|---|---|---|
| mAvailableSongs (set) | 0x1c | 0x2c |
| mUncachedSongMetadata | 0x34 | 0x44 |
| mState | **0x50** (measured) | 0x5c |
| mCachedSongMetadata | **0x54** (measured) | 0x60 |
| mSongIDsInContent | **0x70** (measured) | 0x78 (measured) |
| mContentUsedForSong | 0x8c | 0x90 |
| unkmap5 | 0xa8 | 0xa8 (coincidence) |
| mSongCacheID | 0xc4 | 0xc0 |
| mSongCache | **0xc8** (measured) | 0xc4 (measured) |

So retail SongMgr.cpp TU = **sizeof(map)=0x1c with sizeof(set)=0x18 in the
SAME TU** — exactly the existing `RB3_MAP_0x1C` per-TU gate
(`src/system/stlport/stl/_map.h:85,280`; precedent:
`band3/meta_band/AccomplishmentProgress.cpp` entry in
`config/45410914/objects.json:681`). And **head is 0x10 smaller** than
Hmx::Object(0x28)+Callback(4) — retail SongMgr does NOT have a plain
Hmx::Object first base.

## 5. Open tension the implementer MUST resolve first (decision gate)

If retail SongMgr = MsgSource(+vbase Object) + Callback with members @0x1c,
then MsgSource-sub = 0x18. But `src/band3/game/GameMode.h` (MsgSource-derived,
**matched** unit) annotates its first member `mMode // 0x1c`, implying
MsgSource-sub = 0x1c. Both cannot hold. Possibilities: GameMode's `// 0x` is
stale (known project-wide failure mode), or retail SongMgr's base composition
differs from the naive read. Also note Object is a **virtual base** throughout
the retail UI/rnd hierarchy (see `docs/decomp/research/2026-06-11-uicomponent-virtuals.md`)
— so the 14-slot retail prefix is NOT Hmx::Object's vtable; it is the primary
(MsgSource-led) new-virtual region + possibly more. Do not guess; dump.

Side-note: `scripts/target_symbol_map.json` maps 0x8264C8F0 →
`??_EBandSongMgr@@UAAPAXI@Z`, but the body at fn_8264C828
(`build/45410914/asm/auto_03_8264C238_text.s`) destroys an int-vector @0x2c and
a subobject @+0x4 — shape inconsistent with BandSongMgr (and the listing shows
jeff's known asm mis-nest truncation). Treat that map entry as suspect; don't
anchor the vtable dump on it without checking.
