## The decisive structural insight (why the vein is thin)

`RB3_MAP_0x1C` pads only `std::map`/`std::multimap` (NOT `_Rb_tree`, NOT `set`).
The all-container `RB3_RBTREE_0x1C` pads `_Rb_tree` → grows map AND set. Therefore:

- **map-only flag ≡ all-tree flag** for a TU whose tree containers are *all maps*.
  Such TUs were already settled by the original rbtree campaign (`7cbaa16`,
  `project_rbtree_4byte_deficit.md`): AccomplishmentManager/CharClip kept the flag;
  Song/DirLoader/MusicLibrary were proven byte-identical 0x18-cohort. Re-running
  them under map-only just reproduces those results — confirmed below (all +0).
- **map-only flag = no-op** for a TU whose tree containers are *all sets* (the pad
  is on `class map`, which the TU never instantiates).
- **map-only flag DIFFERS from all-tree ONLY for TUs that embed BOTH a map and a
  set member.** Those are the *only* structurally-new candidates.

Census (`tools/rbtree_blast.py --json`), pinned (matched>0 or scaffold) units with
BOTH map and set members:

| unit | matched | near | containers |
|------|---------|------|------------|
| `band3/meta_band/AccomplishmentProgress` | 45 | 6 | map,set×4,map×4 — **DONE (+10)** |
| `SongMgr` | 0 | 0 | set,map×5 — **1 fn @0%, scaffold** |
| `HamDirector` | 0 | 0 | map×2,set — **1 fn @0%, scaffold** |
| `DanceRemixer` | 0 | 0 | set,map — **1 fn @0%, scaffold** |

The three new map+set units each have exactly **one** pinned function, sitting at
0%. A layout flag cannot register a delta there (nothing matched to shift, and a
single 0% function won't flip to 100% from a layout flag alone — it needs the
source ported first). So the genuinely-distinct map-vs-set vein has no harvestable
target. A/B confirmed all three +0.

## Fingerprint scan (near-miss inventory)

I scanned every near-miss (90–99.99%) in all 28 pinned map/set-bearing units for
the stair-step map-offset signature (uniform +4/+8/+12-per-preceding-map shifts on
*member* `lwz`/`stw`/`addi` accesses, the AccomplishmentProgress dtor pattern). Two
units showed *any* stair-candidate; both are FALSE POSITIVES on inspection:

- **CharDriver::Transfer** (99.818, deltas={+12:8}): the +12 sits on `mTestClip`/
  `mDefaultClip` **ObjPtr** members (`addi r3,r29,0x64`→`0x70`, `lfs 0x74/0x78`→
  `0x80/0x84`) at offsets *upstream* of the map. `mClipWeightMap` is the **last**
  member (after 0xc4), so growing it can't shift 0x64-area members. Root cause is
  an ObjPtr/ObjRef-chain layout delta, not std::map. (A/B confirmed: +0 — map at
  tail, no matched fn touches it.)
- **Gem** (AddInstance 91.6 deltas={+16:61}, AddChordInstance 99.991 {+8:2}): Gem
  embeds only `std::set<TrackWidget*> mWidgets`@0x8 (no map member at all). The +16
  in AddInstance is a **stack-frame** size delta (`r31`-relative locals) plus
  regswaps + body reorder; the +8 in AddChordInstance is a missing scalar member in
  the hand-reconstructed layout (0x4c–0x5c block). Neither is a std::map offset; the
  map-only flag is a no-op for Gem (set-only). Verified the `bl ?insert_unique@
  ?$_Rb_tree@PAVTrackWidget@@…@_SetTraitsT@…` is a SET insert.

Every other unit's near-misses are EH-cleanup **funclet** mis-pairings (single
`[off]` delta + a `bl ??1…@@UAA@XZ` `[sym]` mismatch — e.g. DirLoader `fn_82732CFC`
`~String`↔`~ObjOwnerPtr<ObjectDir>`, MoveMgr `~vector`/`~basic_string` thunks) or
label-pairing `<str>`/`lbl_` noise — none are map-layout.

## Conclusions / updates for the rbtree-ODR story

1. The map-vs-set refinement is REAL (AccomplishmentProgress proved it) but its
   harvestable surface is **exhausted by that one TU**. The only other pinned
   map+set units (SongMgr/HamDirector/DanceRemixer) are unported scaffolds — they'll
   become candidates *if and when their source is ported and functions pair*, at
   which point a map-only A/B is worth a single rerun, not before.
2. The only-map cohort is fully settled and needs no re-test: map-only ≡ all-tree,
   and the all-tree outcomes (AM/CharClip 0x1c; Song/DirLoader/MusicLibrary/
   CharLipSync/NameGenerator/CharDriver/FlowManager/FSS/PropertyEventProvider/
   DefaultPhysicsManager all 0x18) are reproduced here.
3. VocalTrackDir is a genuine **0x18-map cohort** TU (map-only flag regresses it
   −8) — do not flag it.
4. The set-only units (MoveMgr/Gem/MoveAsyncDetector/MoveDir) are no-ops for
   map-only by construction; their near-misses are funclet/body-port/scalar-layout
   work, not container-size.

**Recommendation: close this vein.** No further RB3_MAP_0x1C sweeping is warranted
until a map+set scaffold TU (SongMgr/HamDirector/DanceRemixer) gets its source
ported.
