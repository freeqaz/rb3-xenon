# Wave-5 hashmap lane — AccomplishmentManager + SongMgr hash_map vein (2026-06-16)

Baseline: main @4fe5e05, report.json total **8038**.

---

## Executive summary

The `RB3_RBTREE_0x1C` gate on `AccomplishmentManager.cpp` and the `RB3_MAP_0x1C`
gate on `SongMgr.cpp` were originally added to compensate for member maps appearing
to have 0x1c-byte sizeof. Both are **compensating impostors**: the members are
genuinely `std::hash_map` (sizeof 0x1c naturally from `_M_max_load_factor @0x18`),
not `std::map + pad`. Matching AccomplishmentProgress's bp4 fix (wave-4) proves the
pattern.

The fix: change all `std::map<Symbol,X>` members in AccomplishmentManager to
`hash_map`, update AccomplishmentManager.h (header comment offsets wrong too —
see Finding 2), remove the `RB3_RBTREE_0x1C` gate, add symbol map entries for the
Has/Get functions that use `find()` inline. The same applies to 2 SongMgr members.

**GO. Expected delta: +13 conservative (AM Has/Get simple functions with map
entries added), up to +20 with SongMgr.**

## Finding 1: AccomplishmentManager — all map<Symbol,X> members are hash_map

### The tell: fn_82543F88 called 34 times in AccomplishmentManager.s

`grep "fn_82543F88" build/45410914/asm/band3/meta_band/AccomplishmentManager.s`
→ 34 occurrences. `fn_82543F88` is the ICF-folded hash_map find COMDAT
(proven in bp4 dossier: `build/45410914/asm/band3/meta_band/AccomplishmentProgress.s`
contains its body; the out-of-line `(sret r3, &container r4, &key r5)`, NULL-miss
sentinel, value at `node+0x8` pattern is STLport `_hashtable::find`).

### Container offsets in retail

Every `bl fn_82543F88` is preceded by `addi r4, r3, OFFSET` (r3=this for direct
AM methods, r26/r28/r29/r30 for methods receiving AM* as non-receiver arg).
Unique container offsets: 0x2c, 0x48, 0x64, 0x80, 0x9c, 0xb8, 0xd4, 0xf0,
0x118, 0x134, 0x1a0, 0x1bc.

### Decoding the layout (Finding 2 explains the 0x2c base)

With `data_start = 0x2c` and `hash_map size = 0x1c`:

| offset | member | confirmed? |
|--------|--------|-----------|
| 0x2c | mAccomplishments | ✓ |
| 0x48 | mAccomplishmentCategory | ✓ |
| 0x64 | mAccomplishmentGroups | ✓ |
| 0x80 | mAwards | ✓ |
| 0x9c | mAssetToAward | ✓ (AddAssetAward 100% — `addi r3, r31, 0x9c` matches) |
| 0xb8 | mAwardToSource | ✓ |
| 0xd4 | unkb0 | ✓ |
| 0xf0 | mFanValues | ✓ |
| 0x10c | m_vFanScalingData (vector, not map) | — |
| 0x118 | m_mapGroupToCategories | ✓ |
| 0x134 | m_mapCategoryToAccomplishmentSet | ✓ |
| 0x150 | mAccomplishmentRewardLeaderboardThresholds[4] | — |
| 0x160 | mAccomplishmentRewardIconThresholds[4] | — |
| ... | vectors | — |
| 0x1a0 | mPrecachedFilters | ✓ |
| 0x1bc | mPrecachedFilterCounts | ✓ |

All 12 unique offsets are accounted for. Layout is perfectly consistent with
`all-maps-are-hash_maps`, data starting at 0x2c.

### Why the current 100% fns don't break

Operator[], begin(), end(), clear(), insert() all go **out-of-line** (via bl to
named MSVC map/hash_map COMDATs). Under normalized diff, reloc targets are
ignored → these match 100% regardless of container type. Only `find()` inline
reveals the divergence (produces different asm: inline `_Rb_tree::_M_find` for
std::map vs out-of-line `fn_82543F88` call for hash_map).

The currently-100% AddAssetAward was verified:
```
index 18: addi r3, r31, 0x9c   (target)
           addi r3, r31, 0x9c   (base)   ← matches!
```
The compiler already computes 0x9c correctly from the C++ layout (Hmx::Object +
ContentMgr::Callback vtable = 0x2c base). The header COMMENT saying 0x20 is
stale documentation, not a compiler input.

### The 0x5c inline-find oddity

`?HasAccomplishmentGroup@AccomplishmentManager@@QBA_NVSymbol@@@Z` at 0x825788C8
was compiled into AccomplishmentProgress.obj (ICF COMDAT land). It accesses
container via `addi r31, r3, 0x5c` and calls INLINE `_Rb_tree::_M_find`. That's
0x58+0x4 = map_start + 4 (the `_Rb_tree::_M_find` receives `r3 = &_M_header`
which is at map_start+0x4 in the MSVC STLport build). With 0x1c maps from 0x20
(old layout in that compilation context), mAccomplishmentGroups = 0x20+2*0x1c =
0x58, and `_M_find` called with 0x58+0x4 = 0x5c. **This is a STALE COMDAT from
the AccomplishmentProgress.cpp context compiled with the OLD source layout.** It
does not contradict the hash_map finding.

## Finding 2: header comment offsets wrong by +0xc (ContentMgr::Callback vtable)

`AccomplishmentManager : public Hmx::Object, public ContentMgr::Callback`.

Retail asm stores ContentMgr::Callback vtable at `this+0x28`:
```
stw r10, 0x28(r30)   (build/45410914/asm/band3/meta_band/AccomplishmentManager.s:11365)
stw r10, 0x28(r3)    (line 13068)
```

Hmx::Object = 0x28 bytes on X360 (vptr@0, TypeProps@4, mTypeDef@0x10, mName@0x18,
mDir@0x1c, mRefs@0x20). ContentMgr::Callback adds vptr only → 4 bytes at 0x28.
AccomplishmentManager own data starts at **0x2c**.

Header comments say `mAccomplishments: // 0x20` — this is wrong by 0xc. The
COMPILER generates the correct offset (proven by AddAssetAward 100%); only the
documentation is stale.

**Action: update comments, do NOT change member ordering or type — the compiler
already uses 0x2c.**

## Finding 3: SongMgr — mSongIDsInContent and unkmap5 are hash_map

`grep "fn_82543F88" build/45410914/asm/SongMgr.s` → 7 occurrences.

Container offsets (r3-based):
```
addi r4, r3, 0x70   (mSongIDsInContent)
addi r4, r3, 0xa8   (unkmap5)
```

With SongMgr inheriting from `MsgSource` + `ContentMgr::Callback`:
- mCachedSongMetadata (std::map) @ 0x54, size 0x1c → end 0x70. ← 0x70 CONFIRMED
- unkmap5 @ 0x70 + 0x1c + SongMgrState(4) + 0x1c = need to re-check.

Actually from the header comments already:
```cpp
std::map<int, SongMetadata *> mCachedSongMetadata; // 0x54
SongMgrState mState;                               // (4 bytes inside mCachedSongMetadata range?)
std::map<Symbol, std::vector<int> > mSongIDsInContent; // 0x70
std::map<int, Symbol> mContentUsedForSong;         // 0x8c  
std::map<Symbol, String> unkmap5;                  // 0xa8
```

0x70 and 0xa8 confirmed by retail. mSongIDsInContent and unkmap5 are hash_maps.
mContentUsedForSong (0x8c) — no hash_map find for it, so it may genuinely be
std::map<int,Symbol> (the `int` key uses identity hash, same as hash_map<int,Symbol>,
so hash_map<int,Symbol>::find would also call fn_82543F88; the absence suggests it's
a genuine std::map). **Do not change mContentUsedForSong until confirmed.**

SongMgr currently has RB3_MAP_0x1C gate (objects.json:478). The gate makes ALL maps
in SongMgr 0x1c. But if only mSongIDsInContent and unkmap5 are hash_maps, and
the other maps (mUncachedSongMetadata, mCachedSongMetadata, mContentUsedForSong)
are genuine std::maps needing the 0x1c size, then the gate is STILL needed for
those. The fix is surgical: change ONLY mSongIDsInContent and unkmap5 to hash_map,
keep the gate for the remaining std::map members.
