### fn_82543F88 body = STLport hashtable find, instruction for instruction

`build/45410914/asm/band3/meta_band/AccomplishmentManager.s` (the COMDAT landed
in AM's pinned range — note: that means **AccomplishmentManager uses hash_map
too**, see Follow-ups):

```
lwz r9, 0x8(r4)     ; _M_buckets._M_start        }  hashtable+0x8
lwz r11, 0xc(r4)    ; _M_buckets._M_finish       }  hashtable+0xc
lwz r10, 0x0(r5)    ; key word (Symbol's char*)
subf/srawi 2        ; nbuckets = (finish-start)/4
subi r11, r11, 1    ; bucket_count() = size()-1   <- sentinel bucket
divwu r8, r10, r11  ; _M_hash(key) % n
twllei r11, 0x0     ; MSVC div-by-zero trap
mullw/subf          ; modulo remainder
slwi 2 / add        ; &_M_buckets[n]
lwz r11, 0x0(r9)    ; first = buckets[n]
lwz r9,  0x4(r9)    ; last  = buckets[n+1]
loop: lwz r8, 0x4(r11) ; node->value.first (slist node: next@0, pair@+4)
      cmplw r8, r10 / beq found
      lwz r11, 0x0(r11) ; node->next
      bne loop
...
stw NULL-or-node into sret slot           ; iterator by value
```

Match against our `src/system/stlport/stl/_hashtable.h`:
- `bucket_count() { return _M_buckets.size() - 1; }` (line 359-360, comment:
  "last bucket always contains _M_elems.end()") → the `subi r11,r11,1`.
- `_M_bkt_num_key = _M_hash(__key) % __n` (line 559-561) → divwu/twllei.
- `_M_find` (line 467-478): `__first(_M_buckets[__n]); __last(_M_buckets[__n+1]);
  walk while !equals; return found ? __first : _M_elems.end()` — slist end =
  **NULL** → the `cmplwi r11, 0x0` in callers.
- `find` (line 483-495) wraps in `iterator` (non-POD `_Ht_iterator`) → **sret**.
- Member order (lines 243-249): `_M_hash/_M_equals/_M_get_key` (3 empties,
  pad→4) @0x0, `_M_elems` slist @0x4, `_M_buckets` vector @**0x8** (start@0x8
  finish@0xc eos@0x10), `_M_num_elements` @0x14, **`float _M_max_load_factor`
  @0x18** → **sizeof = 0x1c**.

So:
- sizeof(hash_map) = **0x1c naturally** — the wave-3 RB3_MAP_0x1C pad was
  reproducing this by accident.
- The prior dossier's "dead pad words" at 0x610/0x62c/0x648 = each member's
  `_M_max_load_factor` (0x5f8+0x18, 0x614+0x18, 0x630+0x18) — never touched by
  inlined code paths. Exact.
- `hash<int>` is identity and `hash<Symbol>` (identity on the interned `char*`,
  `lwz r10,0x0(r5)`) generate byte-identical finds → `<Symbol,int>` and
  `<int,int>` instantiations **ICF-fold into the single COMDAT fn_82543F88**,
  which is bl'd from ≥10 TUs (SongMgr.s, DataFunc.s, auto_03_* blobs — grep
  `fn_82543F88` under build/45410914/asm/).

### Source-provenance corroboration

`/home/free/code/milohax/rb3/src/system/meta/FixedSizeSaveable.h:131-180` —
the rb3-Wii decomp's reconstructed signatures say `const std::map<Symbol,T>&`,
but the **original MILO_NOTIFY string** says
`"The hash_map size is greater than the maximum supplied! ..."` and
`"hash_map is not empty!"`. The original Harmonix type was `hash_map`; the Wii
decomp's `std::map` is an MWCC-era approximation. Same strings in our
`src/system/meta/FixedSizeSaveable.h:148,174,272,...` and DC3's.

Fifth member proven the same way: unpaired target `fn_82579510` (sz80) is
byte-identical find-shape on member **@0x30** → `mStepTrackingMap` is also a
hash_map, and the fn is `?GetCurrentValue@AccomplishmentProgress@@QAAHVSymbol@@@Z`
(our source already defines it: AccomplishmentProgress.cpp:920, oracle
../rb3/.../AccomplishmentProgress.cpp:923).

Why currently-matched fns didn't expose this: `SetToursPlayed`/`SetMostStars`/
`SetToursGotAllStars`/`SetQuestCompletedCount`/`SetCurrentValue` (all 100%) call
operator[] **out-of-line** — `bl <COMDAT>` is reloc-blind under normalized, and
the caller marshalling (&container, &key → returns value&) is identical for map
and hash_map. Likewise the AccProg dtor + funclets call member dtors via bl
(shape-identical). The find-inlining Get* quad is exactly where the impostor
leaks.

### Wii-vs-360 reconciliation

This does NOT mean Wii used map and 360 used hash_map: the Wii **decomp**
chose `std::map`; the save-format strings show the original was hash_map on
both. (Wii MWCC hashtable codegen evidently matched loosely enough or the Wii
container was never byte-verified.) For porting we follow the retail asm.

## Finding 2: GamerAwardStatus is missing its Xbox-360 async-write tail (XOVERLAPPED @ +0x1c), retail sizeof = 0x38

Our class (`src/band3/meta_band/AccomplishmentProgress.h`, mirrors rb3-Wii
exactly): `vptr@0, mSaveSizeMethod@4, unk8, unkc, unk10` → sizeof 0x14. Retail
evidence says the 360 build added members the Wii build never had:

1. **`??0GamerAwardStatus@@QAA@XZ` 70.11 sz108 (ours 92):** retail extra block =
   `addi r3,r31,0x1c; li r5,0x1c; li r4,0; bl memset` →
   **memset(this+0x1c, 0, 0x1c)**. 92 + 16 = 108 — size closes exactly.
2. **`??0GamerAwardStatus@@QAA@HW4GamerAwardType@@@Z`** (target fn_82578190,
   sz96, already in scripts/target_symbol_map.json:10194, base-side MISSING):
   `stw arg1@0x8, stw arg2@0xc, stb 0@0x10, memset(this+0x1c,0,0x1c),
   stw &SaveSize@0x4, stw vtable@0x0` — full body recovered from
   build/45410914/asm/band3/meta_band/AccomplishmentProgress.s:1387-1414.
3. **`??1GamerAwardStatus@@UAA@XZ` 19.0 sz80 (ours 16):** retail:
   ```
   stw vtable; addi r3, r3, 0x1c
   lwz r10, 0x1c(r31); cmplwi cr6, r10, 0x3e5; bne skip
   bl fn_828165E8           ; (r3 = this+0x1c)
   skip: mr r3, r31; bl ~FixedSizeSaveable
   ```
   **0x3e5 = 997 = ERROR_IO_PENDING.** The +0x1c member is an **XOVERLAPPED**
   (7 words = 0x1c on X360: InternalLow first) and fn_828165E8 is
   `XCancelOverlapped`-family. DC3 oracle has the identical idiom:
   `../dc3-decomp/src/system/os/PlatformMgr_Xbox.cpp:664,744,759`
   (`mOverlapped.InternalLow == 0x3e5`). GamerAwardStatus is the 360
   achievement/award async-write status object — that's WHY the Wii oracle
   lacks the members.
4. **LoadStdPtr template @99.98 sz232:** single diff_arg at idx 29:
   target `li r3, 0x38` vs base `li r3, 0x14` = `operator new(sizeof(GamerAwardStatus))`.
   Pure size-constant; flips to 100 with the class fix.

Retail layout: `0x14 unk14 (int, never ctor-init), 0x18 unk18 (int, never
ctor-init), 0x1c XOVERLAPPED mOverlapped (memset-zeroed in both ctors)` →
sizeof **0x38**. `SaveFixed`/`LoadFixed` (both 100% today) only touch
unk8/unkc — unaffected.
