## 1. The MCP server's main-repo fallback

### ⚠ FIRST: the evidence that motivated this item was RETRACTED

The brief cited two incidents — 642 objects rewritten at 23:31 UTC on 09-10 and
37 objects between 00:24 and 00:50 on 09-11 — as proof the fallback had fired.
**The coordinator retracted both on 2026-09-11** (landed on main as `44604283`,
*"RETRACT the drift incidents as evidence of out-of-graph builds"*): a full
`./tools/ninja-locked` rewrites objects **progressively** and only rewrites
`patch_state.json` at its **terminal** edge, and the verifier never takes
`.ninja-build.lock`. So **any `--verify-manifest` sample taken while a build is
running** reads "objects changed, manifest stale" and the tool prints *"produced
OUTSIDE the full build graph"* as fact. Both incidents are consistent with a
build in flight; the 37-object one was almost certainly the coordinator's own.

**This is written down so the next reader does not re-inherit it.** Everything
below is a defect that is *reachable by construction*, demonstrated on the code;
none of it rests on those incidents. A peer lane (GATE-DISC) is adding a
BUILD-IN-PROGRESS verdict to `verify_objs_patched.py`; this lane did not touch
that file.

### The mechanism, as actually found

`mcp_server.py` had **three** copies of "which tree do I measure?", and they had
already drifted:

| handler | `project_dir` absent | `ensure_patched_tree` |
|---|---|---|
| `run_objdiff` (was line 1746) | → `self.project_root` = **main** | ✅ yes (line 1826) |
| `run_analyze_function` (was 2094) | → `self.project_root` = **main** | ⛔ **no** |
| `run_diff_inspect` (was 2213) | refused already | ✅ yes (2227) |

A rule enforced in two of three places is not a rule. `self.project_root` is
`Path(__file__).resolve().parent.parent.parent` and the server is launched from
the shared checkout (`.mcp.json` lives there), so for the whole fleet that
default **is main**. A subagent that omits `project_dir` and has no `REPO_ROOT`
— the normal state of a subagent — therefore (a) measured MAIN instead of its own
edits, in a shape indistinguishable from *"my change did nothing"*, and (b) built
in the shared tree.

**Two things the brief expected that I did NOT find, stated because they change
the diagnosis:**

* **`run_objdiff` does NOT do a targeted `.obj` build.** It passes no `--build`
  (`build_flag = []`) and goes through `ensure_patched_tree`, which builds
  `post-compile` and then asserts. The CLAUDE.md note *"`run_objdiff` skips the
  patchers"* was fixed upstream in `4ba12257`. So the fallback's harm is **a
  wrong answer and a build in a shared tree**, not an unpatched tree — which is
  independently why the retracted incidents could not have been caused by it.
* **`run_analyze_function` is DEAD.** `bin/analyze-function` does not exist in
  main or in a worktree (`bin/` holds only `objdiff-cli`), so every call has
  always returned the not-found error. Its missing patch guard was therefore
  harmless; I added it anyway so that resurrecting the script does not resurrect
  the gap.

### 1b. The mechanism that CAN leave a tree unpatched — and it is worse

Tracing *what build command each path runs* turned up a real one the brief did
not name. `_run_asm_listing` (reachable as `run_diff_inspect mode:"asm_listing"`)
does:

```
ninja -t commands <obj>      →  reuse that command verbatim + " /FAs /Fa<tmp>"
```

Verified literally on this tree, for `build/45410914/src/system/obj/Object.obj`,
the emitted command contains the object path **twice**:

```
objcache exec --fo build/45410914/src/system/obj/Object.obj -- … cl.exe …
    /Fobuild/45410914/src/system/obj/Object.obj src/system/obj/Object.cpp
```

So every `asm_listing` call **overwrote the tree's patched object with raw
compiler output, outside the build graph.** And it is *worse* than the
`ninja <one>.obj` hazard CLAUDE.md documents: a targeted `.obj` build at least
leaves the object older than nothing, whereas this leaves it with an mtime
**newer than its inputs**, so ninja then considers the edge up to date and
**never repairs it**. The tree stays silently unpatched until something unrelated
invalidates that edge, and every measurement from it is biased low. Its `/Fa`
listing went to a temp dir, which is exactly why the object write was easy to
miss.

Fixed by `redirect_compile_object()`, which rewrites every occurrence of the
object path and **raises** when it finds none: *"could not redirect"* must never
degrade into *"wrote to the tree"*.

### The fix

One pure function, `resolve_project_dir(arg, main_repo, env)`, used by all three
handlers. Precedence is unchanged for legitimate cases (explicit arg >
`REPO_ROOT`) but there is **no third tier**.

* **An absent `project_dir` refuses.**
* **An explicit `project_dir` naming main also refuses.** Same measurement of the
  same shared tree; a hazard is not neutralised by being typed out. It is also
  the only route by which a tool that already *required* `project_dir` could
  reach main.
* Comparison is by **resolved** path, so `main/.` and a symlink to main both
  refuse. A string compare would have let the fallback back in through the front
  door — and the sabotage arm for it is a separate defect precisely because that
  is an easy "simplification" for a later reader to make.
* `RB3_MCP_ALLOW_MAIN=1` is the opt-in, deliberately an **env var, not a tool
  argument**: measuring main is a legitimate coordinator action but it is a
  property of the *session*, not of one call, and an argument would be reachable
  by any model that read the docstring and wanted its call to succeed.

Both new functions take `main_repo`/`env` as **arguments** so they are testable
without a server, an MCP client or a second checkout. The old logic was reachable
only through a live async handler — nothing ever asked it anything, which is
precisely why the drift between three copies survived.

### The control

`scripts/sabotage_project_dir_guard.py` (registered in `test_tools.py`'s script
arm). It extracts the guard region from the **real** `mcp_server.py` — the file
cannot be imported from a sandbox — sabotages it seven ways and requires the
**named** test to go red for each:

```
[sabotage] baseline green on the extracted region
  [caught] restore the three-tier main-repo fallback (THE original defect)
  [caught] accept an explicitly-spelled main repo
  [caught] compare paths as STRINGS, so `main/.` and a symlink slip through
  [caught] treat any non-empty RB3_MCP_ALLOW_MAIN as true (so `=0` opens the door)
  [caught] default env to {} instead of os.environ (REPO_ROOT becomes invisible)
  [caught] let the compile redirect fall through instead of refusing
  [caught] redirect only the FIRST output path, leaving /Fo on the tree's object
  [ok]     null arm: no-op edit (the harness's own control) broke nothing, as required
[sabotage] 7/7 caught by the intended test, 0 not caught (or caught vacuously)
```

Three anti-vacuity properties, each because the obvious version of this harness
would have lacked it: it **refuses** if the extraction markers stop matching or
the slice stops defining the names the test imports (a sweep over an empty slice
would report a clean 7/7); it **refuses** on a red baseline (which would make
every sabotage look caught); and the **NULL arm** requires a no-op edit to break
nothing.

### Deployment note

**A server restart IS required.** This is a source change to a stdio MCP server
that other sessions have already imported; a running server keeps the old module
in memory and will keep falling back to main until it is relaunched. I did **not**
restart or kill anything (hard rule), so until each session restarts its server,
the refusal is not in force for it.

## 2. `crossing_worklist.py` — the truncated symbol column

### The mechanism is NOT a plain truncation, and the difference is load-bearing

Lane L5-SYMBOLHEADS handoff 5 reported that row 12 was briefed as
`?SelectNode@MusicLibrary@@QAAXPAVSortNode@@PAVLocalBandUser@@@Z` while the real
name ends `@@_N@Z`. Measured here:

| | value | length |
|---|---|---:|
| real name (present in `report.json`, `default/MusicLibrary`, 2,260 B) | `?SelectNode@MusicLibrary@@QAAXPAVSortNode@@PAVLocalBandUser@@_N@Z` | **65** |
| briefed name | `?SelectNode@MusicLibrary@@QAAXPAVSortNode@@PAVLocalBandUser@@@Z` | **63** |
| `real[:58]` — what the column actually printed | `?SelectNode@MusicLibrary@@QAAXPAVSortNode@@PAVLocalBandUse` | 58 |

★ **The briefed name is not `real[:58]`.** The two share *exactly* the first 58
characters and then diverge: the tool's cut landed **mid-token**, and because
there was **no ellipsis** the name was then *reconstructed* to a plausible
mangled terminator (`...User@@@Z`) — producing a well-formed symbol that is wrong
in its last five characters. So the defect is not "the name was short", it is
**"the cut was invisible, so it got repaired into a confident lie"**.

That is why objdiff's answer — *"Symbol not found in target"* — reads like a
**phantom row** (a dtk mis-carve, a class this project genuinely has) rather than
like a copy error, and the row gets written off instead of retried.

⇒ **An ellipsis marker would be an improvement and is still not enough.** These
names are copy-paste *input* to `objdiff-cli` and to the map, so anything short
of the full name is unusable. Alignment is not worth a wrong symbol.

### What was fixed

**Five** truncation sites, not the one reported — every one a line whose whole
purpose is to name a symbol a human must re-run:

| site | old width |
|---|---:|
| the worklist's symbol column (`cmd_census`) | 58 |
| `diff_many`'s `STABLE MISS` diagnostic | 70 |
| control 1b's pin-nominee list | 70 |
| control 1b's subject line (had an honest `...`) | 38 |
| `adjudicate()`'s FAIL list | 86 |

The symbol now goes **last** on every line, so a long one cannot misalign a
column. Rendering moved into a pure `format_worklist_row()` so it is assertable
without a tree.

### The control

New `--selftest` **control 5**: render a **constant** 65-char witness and require
the full name to appear. Constant on purpose — unlike controls 1b/2 it cannot
*disarm* when the live row is fixed upstream (and this row **was** fixed: it now
reads `fuzzy 100.0`, so a control pinned to the live population would already be
dead). It is a **rendering** assertion, not a `len()` on the row dict, because
the defect was in what got printed.

`--self-break` now **reinstates** the 58-char cut rather than simulating it,
matching the existing pricing sabotage. Proven to discriminate:

```
FIXED  : … default/MusicLibrary   ?SelectNode@…@@PAVLocalBandUser@@_N@Z   full name present? True
BROKEN : … default/MusicLibrary   ?SelectNode@…@@PAVLocalBandUse          full name present? False
```

The broken form ends exactly `...PAVLocalBandUse`, reproducing L5 byte-for-byte.

⚠ **Two bugs in my own first cut, both of the class this lane is about.** Control
5 was first placed **below** `if fails:`, so its `fails.append` could never be
read — a control that cannot fail, added by the lane whose job is removing those.
And `summarise(out=sys.stdout)` bound the stream at **import** time, so pytest's
capture saw nothing; the test caught it.

### The cache: v3 → v4

**The ruler was already in the key** — landed by lane T2-RULER as `d1b4f708`,
which is a commit in this lane's own briefing snapshot. So half of the briefed
request was already done; the brief was stale. What was **not** in the key is the
**objdiff binary**, and v3's own comment shows the gap precisely:

> *"A cached measurement is only comparable to a fresh one if it was taken with
> the same instrument."* — and then it keyed on the ruler, which is the
> instrument's **configuration**, not the instrument.

`bin/objdiff-cli` is a symlink into a shared build tree that three repos share
and it is swapped **in place** — main's log records two swaps in one day
(`5aa1cb7a`, *"the second objdiff swap of the day is SCORE-NEUTRAL on this
binary"*). A swap changes mismatch counts and charged-site kinds while leaving
`sym`, `unit` and the ruler key identical, so v3 served pre-swap entries to
post-swap runs without a word. `InputStability` already VOIDs a run whose
`objdiff-cli` moves **mid-run**; that says nothing about an entry minted last
week.

v4 keys on **both** identities, because they can disagree:

* `report.json` `provenance.tool_binary_hash` — the binary that produced the
  **population** and the prices we rank against (here `14ac591a0814e6c9`, objdiff
  `4.2.8`), and
* the content hash of the **live** `bin/objdiff-cli` — the binary that actually
  mints this entry.

⇒ Keying on the report's hash alone — the obvious reading of the request — would
miss exactly the motivating case: **a binary swapped under a `report.json` nobody
has regenerated yet.** An unknown instrument keys as the literal `unknown`, a
*different* key from every known one, so the failure mode is "recompute", never
"serve an entry from an instrument we cannot name".

### What happens to the old entries

**Nothing is deleted, and nothing stale is served.** The key *changed*, so v3
files are **unreachable** rather than stale-and-served. Measured at the start of
this lane the shared dir held **11,120 entries / 420 MB**, so this is real disk:
`cache_note()` now prints the inventory and the reclaim command **once per dir
per run** (observed live: `[cache] 11,122 entr(ies), 417 MB … rm -rf … to
reclaim`). Deleting them is safe and costs one re-mint pass (~7 min at 8
workers). It is a NOTE, never a refusal — an orphan entry cannot corrupt a
measurement, it only costs space.

Two smaller stale premises in the brief, both tested literally before building on

### The criterion (CONTAINER2 §1)

`matched_code` is **all-or-nothing per row**, so a row crosses only when **every**
charged site on it resolves. A mismatch-count band is a different question, and it
is wrong in **both** directions:

* it **admits** a 3-charge row with one container site, which does *not* cross
  when the pair is fixed;
* it **misses** an 8-charge row whose every site is a container site, which does.

The census already had the data — `diff_one` returns every charged site *with its
kind* — and threw it away. It now records per row `row_sites`,
`row_container_sites` and `fully_covered`, and `summarise()` prints the candidate
class, the **crossing** population and the **refuted band** side by side from one
run. One run on purpose: the gap between them is the interesting quantity and two
runs could not establish it, because the population moves under every map repair.

`fully_covered` is **False** for a row with zero charged sites, deliberately: an
`all()` over an empty list is vacuously True and would promote every row objdiff
returned nothing for into the realisable prize — the `all([])` trap CLAUDE.md
names elsewhere.

### The label (CONTAINER2 §6): `NOFOLD` → `NOT_REFUTED_BY_MAP`

`NOFOLD` asserted *"provably did not fold"* on the premise that the map's name at
each consulted address is right. L7 **measured** that premise:

| family | map names checked | provably wrong | rate |
|---|---:|---:|---:|
| `~ObjRefConcrete<T>` (vtable/RTTI) | 70 | 30 | **43%** |
| `list<T*>::insert` (node size) | 8 | 6 | **75%** |

The rate now travels **with the label in the tool's output**, not in a doc nobody
re-reads, because L7's headline pair is a case where a reader who stopped at
"NOFOLD" would have concluded the **exact opposite** of the truth:
`list<CharClip*>::insert` vs `list<Object*>::insert` was labelled NOFOLD because
the names sit at different addresses — but `0x823c3ac8` is not
`list<Object*>::insert` at all (24-byte node, copy-constructs a
`CharIKHand::IKTarget`), so the premise rested on a wrong name and **the
pointer-element family DID fold**. A caveat in prose would not have reached that
reader; the label does.

### ⛔ THE BRIEFED "3.1× TOO SMALL" DOES NOT REPRODUCE — it is 0.95× here

The brief (and CONTAINER2 §1) prices the criterion change at **3.1×**. Measured
on this tree the crossing population is **0.95× the band by bytes** and 0.93× by
rows. **Tested literally before being built on, per CLAUDE.md, and it fails.**

This is not a refutation of the criterion — it is a refutation of the *number*,
and the distinction matters because the number is what gets briefed:

* **L7's 3.1× was never a controlled comparison of the two criteria.** It divided
  L7's own crossing figure (61,952 B, measured with the census instrument) by
  **its brief's** band figure (19,792 B, computed elsewhere, on a different row
  population). Two instruments, one ratio. My run computes **both criteria with
  one instrument on one tree**, which is the only way the ratio means anything.
* **The criterion difference is real, but it is a SET difference, not a size
  difference.** The band admits **19 rows / 3,848 B that cannot cross** (false
  prize) and misses **3 rows / 2,012 B that can** (invisible real prize) — exactly
  the two directions §1 names. The two populations are nearly the same *size*
  while disagreeing about **22 rows**.
* **Why the shapes coincide here:** the charged-site distribution over candidate
  rows is `{1: 173, 2: 29, 3: 12, 4: 4, 5: 3, 7: 1, 9: 1, 24: 1, 26: 1, 27: 1,
  48: 1, 52: 1}` — **75% of the class carries exactly one charge**, and only 14
  rows exceed 3, of which just 3 are fully covered. The "8 charges, all container"
  shape that makes the band look small is **rare on this tree**. On a tree where
  it is common the ratio would be large again.

⇒ **Use the crossing criterion because it is the right question** (`matched_code`
is all-or-nothing per row), **not because it is 3.1× bigger.** Anyone re-briefing
this class should quote the set difference and re-measure the ratio.
