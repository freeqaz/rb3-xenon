## 1. Item 4 — the one that paid: `GetTrackInstrument` (+676 B, predicted exactly)

`0x822BB4E8` was carved into `Waypoint.cpp`'s pin as the anonymous 0% row
`fn_822BB4E8`. It is retail's `GetTrackInstrument`, the callee behind every
`GetTrackInstrument` site in `BandCrowdMeter::Handle`, whose body L6 ported
yesterday **to fix the caller** (retail's `Handle` re-sets `mr r4, r30` *after*
the `bl` because the callee clobbers r4). Byte-exactness was therefore an open
question, not a given — the port was driven by a register-clobber signature.

It is byte-exact. Pin moved + address named ⇒ `fuzzy = mpn = 100.0` at 676 B.

**The name must come from our own COFF, and here that is load-bearing beyond
this row.** `?GetTrackInstrument@@YA?AW4TrackInstrument@@VSymbol@@@Z`, read from
`BandCrowdMeter.obj` (sc=2 EXTERNAL, sec=222). Naming a previously-anonymous
address converts a **forgiven** placeholder call target into a **checked** one at
every call site, so a wrong spelling would have charged `BandCrowdMeter::Handle`
(1,384 B, itself only just crossed) and `TrackPanel.cpp`'s four sites. Both
callers spell it identically because both compile against one declaration, so the
conversion cost nothing — confirmed by `Handle` holding 100 across the A/B.

Neither half pays alone, which is why they are one change: `Waypoint.obj` does not
define the symbol (and must not), so the name alone would point at a base obj
that cannot define it — a permanent 0%; and the pin alone is pure reattribution of
an anonymous row, the Δ0 shape `f7bb7bbe` already measured.

## 2. Item 2 — the zero IS the finding: `??_GCharWeightable` exposed a real divergence

L1 handed this over as "+88 B if paired", premised on the body being
"word-identical to our `??_GCharWeightable@@UAAPAXI@Z`". The pin move and the name
are both right and the row does pair — **but the premise was false and the bytes
do not come.** 21 of 22 words match; the 22nd is a genuine callee divergence the
anonymous row had been hiding:

```
[14]  target  bl ?MemFree@@YAXPAX@Z            <- retail: the 1-arg global
      base    bl ??3CharWeightable@@SAXPAX@Z   <- ours: a per-class operator delete
```

Retail's CharWeightable has **no class-level `operator delete`**; ours does,
because `char/` headers came from DC3 and DC3 spells `OBJ_MEM_OVERLOAD` (47
classes in `char/` alone). Both `OBJ_MEM_OVERLOAD` and rb3-Wii's
`DELETE_OVERLOAD` emit a `__declspec(noinline) static void operator delete` over
the **4-arg** `MemFree`, so neither spelling can produce retail's direct `bl` to
the 1-arg `?MemFree@@YAXPAX@Z`.

★ **The `none`-ruler leg sizes it precisely: Δ +88 B on `none` against Δ +0 B
graded.** A name-blind ruler collects the whole row, so the entire 88 B is gated
on that one relocation name and nothing else. (Quoted as a size; `ab_measure`
correctly labels the none control NOT_APPLICABLE *as an alias verdict* on a
splits patch, and it is not read as one.)

⚠ Note `[8]` is **not** charged — target `bl fn_822C2228` vs base
`bl ??1?$ObjOwnerPtr@VCharWeightable@@@@UAA@XZ` — because objdiff forgives a
placeholder target name. A naive charge count reads two defects here; there is
one. This is the standing "charge counting closes open rows" trap, live.

**Kept at Δ0** on the accuracy directive: the row is now in the right unit under
its right name, and an invisible divergence is a metric-visible 99.77% witness —
exactly what `ObjMacros.h` says the follow-on mem-overload classes lack
("METRIC-INVISIBLE today"). This is MAPID-1 repeating: the payout of naming an
anonymous address is **bug exposure, not bytes**. No alias was installed;
forgiving this pair is precisely what `ObjMacros.h:807` says not to do.

## 4. Item 5 — REFUTED: it is the scatter-include architecture, not a mis-pin

L5-SYMBOLHEADS handoff 4 reported `?Handle@Synth@@` (`0x826fee60`) scored inside
`CharMeshHide.cpp` and `Synth::Find<Object>` (`0x826fe3a8`) inside `Sfx.cpp`,
calling it misleading-but-harmless attribution.

Two corrections, in order of importance:

1. ⛔ **It is not harmless — both rows read `fuzzy = 100.0` where they sit.** The
   record's "not score-affecting (rows pair by name)" is wrong about the
   direction of the risk: re-homing them put **2,448 B at risk** for zero upside.
2. ⛔⛔ **And it is not a mis-pin.** There is a deliberate scatter-include chain

   ```
   src/system/char/CharMeshHide.cpp:136   #include "synth/Sfx.cpp"      // sw2 scatter-include
   src/system/synth/Sfx.cpp:305           #include "synth/Synth.cpp"
   src/system/synth/Sfx.cpp:320           #include "world/CameraShot.cpp"
   ```

   with an explanatory comment that **names the very pairing the record flagged**:
   `// sw2 scatter-include (default/CharMeshHide <- synth/Sfx.cpp)`, plus
   `#define gRev gRev_Sfx` collision guards around it. `CharMeshHide.obj`
   therefore **defines `?Handle@Synth@@` on purpose** (confirmed in its COFF
   table, sc=2 EXTERNAL sec=3789), which is exactly why the row pairs and scores.

⇒ **No action taken.** The pin is the architecture working. Re-homing would have
been churn at best; and for `Find<Object>`, a template COMDAT, "the true owner" is
not even determinable from retail bytes — the linker picks one definition.

★ The transferable lesson: **before calling a pin mis-attributed, check whether
the unit is a scatter-include container.** A unit whose obj deliberately compiles
another TU's source will always look like it is claiming foreign code.

**6a AccomplishmentSongConditional.** The 5,212 B block holds 40 functions and

and three independent numbers reconcile to that list **to the byte**:

| measure | value | why |
|---|---:|---|
| Δmatched | −10 | all ten sit at `mpn == 100` |
| Δmatched_code | −256 B | only the eight at `fuzzy == 100` feed `matched_code` (8 × 32) |
| Δ on `none` ruler | −336 B | name-blind also collects the two 99.5 rows (10 rows, 336 B) |
| **Δhonest** | **+0** | **zero honest matches lost** |

A 32-byte EH funclet is near content-free, so it pairs with essentially any 32 B
funclet our obj emits; six of these are a consecutive run
(`0x825EBD50..0x825EBDF0`). They unwind the **foreign** functions in the block, so
they are foreign too: the pin was manufacturing 100% rows for code the TU does not
contain. That is the masked-class false-pairing mechanism, caught in the act.

**6c RetryAudioPanel.** End trimmed `0x826319F4 -> 0x82631130`. Predicted Δ0;
measured **−4 fns / −128 B**, same mechanism (`fn_82631260`, `fn_826315A0`,

Both landed on the standing directives that accuracy beats headline % and that a
code% drop from a **truer** denominator is a win. Unit figures become honest:
AccomplishmentSongConditional `total_code` 9,796 → ~4,600 (code% 28.62 → ~61),
RetryAudioPanel 5,704 → ~3,460 (24.12 → ~39.8), `matched_code` unchanged in both.

⇒ **Generalised prediction for any future foreign-block trim: expect the cost to
be `-(number of EH funclets in the ceded range)` matched functions at 32–40 B
each, and expect Δhonest = 0.** Pre-register that shape, not zero. This lane
registered 0 twice and was wrong twice in the same way.

address the function does not live at. Every scan in this lane is keyed on the

## 7. Mechanisms worth reusing

1. ★ **Ask whether the CURRENT unit's obj already defines the symbol before
   assuming a pin move is needed.** `?Handle@Synth@@` is a COMDAT in
   `CharMeshHide.obj` *and* `Synth.obj`; if the current obj defines it, a map name
   alone pays and no splits edit is required. Conversely `CharPollGroup.obj` does
   **not** define `??_GCharWeightable` and `Waypoint.obj` does not define
   `GetTrackInstrument`, so those genuinely needed both halves. One COFF dump
   answers it.
2. ★ **dtk's derived `.pdata` is a free second opinion on the extent you chose.**
   Item 4 moved exactly one 8-byte RUNTIME_FUNCTION record; item 2 the same; item 3
   **merged** two adjacent records; item 6a dropped a range and correctly added no
   replacement for a retained 16 B leaf dtor (no stack, no LR ⇒ no unwind record).
   Each is an independent corroboration, and it is free — edit `.text` only and read
   what dtk writes back.
3. ★ **split-guard firing on the first build of every splits edit is by design**,
   not a failure: `.pdata` is derived, dtk rewrites its own input, and the retry is
   the fixed point. Five for five here.
4. ★ **`Δmasked_equal` vs `Δhonest` is the instrument that tells you whether a
   metric loss was real.** Two of this lane's losses are entirely masked; reading
   `Δmatched` alone would have made them look like regressions to revert.
