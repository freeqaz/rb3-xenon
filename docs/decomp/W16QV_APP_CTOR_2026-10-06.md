## 2. Map: the two checksum wrappers

`0x82272E40` and `0x82272E50` are two 16-byte wrappers. Each tail-calls
`SetFileChecksumData(FileChecksum *, int)`, which appends a table:

| wrapper | table | entries | first entries |
|---|---|---|---|
| `0x82272E40` | `0x82C64A60` | 1,065 | `./char/gen/anim_genres.dtb`, `./char/gen/anim_groups.dtb` |
| `0x82272E50` | `0x82C6AE38` | 62 | `29fingers.mid`, `areyougonnabemygirl.mid` |

The map had `?SetFileChecksumData@@YAXXZ` on `0x82272E50`, the song-MIDI table. The
1,065-entry table of game files is the analogue of the single `SetFileChecksumData()` in
the RB3 game source (1,029 entries) and in DC3. The name was moved to `0x82272E40`, and
`0x82272E50` was left unnamed. Its retail name is not attested. Our source calls it
`SetSongMidiChecksumData()`, and the header says that name is descriptive.

Safety: `App::App` is the only caller of either wrapper. Both rows sit in a mis-pinned range
under `Object.cpp`, and no base object defines either name. So the move changes no row's
pairability. It only changes which call site is charged. The A/B (§4) shows no unit other
than `App` moved.

`0x82270E68` was named `??0App@@QAA@HPAPAD@Z`.

## 3. The residual: one `add` operand order (not closed)

The only charge in `App::App` is in the `persistent_filecache` loop:

```
retail  lwz r11,0(r30); mr r4,r30; add r3,r11,r28; bl DataNode::Str   (mNodes + i*8)
ours    lwz r11,0(r30); mr r4,r30; add r3,r28,r11; bl DataNode::Str   (i*8 + mNodes)
```

Every register and the scheduling are identical. Only the operand order of this commutative
`add` differs. `mpn` is 100, because a register-only argument difference is not charged
there. `fuzzy` is 99.97854, so the 1,864 B are withheld from `matched_code`.

What was tried. Each in-tree variant was a full build plus objdiff (graded ruler). Each
scratch variant was a single `cl.exe /FAs` compile of a minimal TU in `~/tmp/w16qv_scratch`.

- In-tree, all tied at 99.97854 or worse: `Node(i).Str(cacheCfg)`; `const DataArray *`;
  loop variable hoisted (`int i;` before the loop, or before `new`); `while` loop; `++i`;
  a named `FilePath` for `""`; named `FilePath`s for both arguments;
  `gPersistentCache` in an anonymous namespace (the DC3 spelling).
- Worse: `Str` result in a local (+4 instructions, frame 0x250→0x260); explicit
  `FilePath(...)` temps (+8 B); `cfg->Size() > i` (99.946); `Int(1)` into a local (97.66);
  `DataNode &n = Node(i)` (97.998); `Str(nullptr)` (99.85).
- Scratch: the loop alone, without the rest of `App::App`, already compiles IV-first. So
  the cause is not the surrounding function. Ten more spellings of the loop and of the
  `new FileCache` block stayed IV-first: `i += 1`, a `do/while`, an alias pointer, a
  hoisted `const char *""`, `Node(i).Str()`, `LiteralStr`, `true` for the int argument,
  `if (DataArray *c = ...)`, `!= nullptr`, and `SystemConfig(Symbol(...))`. A `short i`
  changes the allocation.
- Scratch finding: the same retail compiler emits mNodes-first for
  `FileMatch(file, cfg->Str(i))` when `file` is a live parameter. It emits IV-first for
  `FileMatch("x", cfg->Str(i))`. So the order tracks how the value graph is numbered, not
  the spelling of the index. Retail has both orders (16 mNodes-first and 14 IV-first sites
  before a `DataNode::Str` call). `XboxContentMgr::StartRefresh` uses our exact spelling
  and reads 100 with mNodes-first.

Not tried: the permuter. It is deferred by standing directive, and this is the class it
exists for. The row is a clean single-instruction target if that changes.
