### 2.1 MEMBER_OFFSET is mostly *not* struct layout

A uniform member-offset delta on one base register is the classic "DC3 added or
dropped a member" force multiplier, so this lane screened for it. The screen
needs a control, because a *permutation* of the same offsets across the same
slots is **load scheduling**, not layout — the multiset of offsets is then
identical on both sides.

| MEMBER_OFFSET sites on the SAME base register | 1,912 |
|---|---:|
| PERMUTATION (identical offset multiset ⇒ scheduling) | 106 sites / 25 rows |
| genuine shift (an offset present on one side only) | 1,806 sites / 240 rows |

Only 5.5 % are permutations — but that 5.5 % includes the two rows this lane
would otherwise have opened as struct bugs, so the control earned its keep.
⚠ The remaining 94.5 % is **not** 94.5 % struct divergence either: the screen
cannot tell `this` from the frame pointer, and spot-checks show most
large-delta rows are frame-slot assignment (e.g. `BandDirector::Enter`, whose
20 "uniform +8" sites are all `r31` = frame pointer after a `subi r31, r1,
0x120` vs our `0x110`).

## 4. The NgStats sequence — how a right count with a wrong cause was caught

This is worth recording in full because the first two attempts were *measured*
wrong, and the instrument that convicted each of them was different.

**Attempt 1 — "retail has no `mMultiMeshBatches`, gate it and its prints to
`HX_NATIVE`."** Evidence: retail's `EstimateDraw` @0x82B87200 addresses the
twelve `NgStats` fields its source expression names at 0x4,0x8,0xc,0x10,0x14,
0x18,0x1c,0x20,0x24,0x28,0x2c,0x30 — twelve **consecutive** words, whereas our
layout must skip 0x2c to reach `mFlares`/`mMotionBlurs`. Corroborated by a
string probe: `"multimesh batches"` has **zero** occurrences in retail
band.exe while its neighbours `"flares %d"` and `"motion blur %d"` have two
each; and the field is incremented **nowhere** in this tree.

Pre-registered Δ0 with a stated risk that `NgRnd::UpdateOverlay` (fuzzy 99.73)
would regress. **Measured Δfuzzy −0.001213 pp with the `none` control at
exactly −1,052 B — the size of `UpdateOverlay`.** The risk fired: that row fell
off 100 on `none`.

**Attempt 2 — move the field to the tail instead of deleting it**, so no
function body changes. **Measured Δfuzzy −0.000003 pp and `none` still
−1,052 B.** Now two retail functions appeared to contradict each other about
the same struct, which is the signature of a mis-paired row (cf. §5) — or of a
wrong premise.

**Resolution — read the third instrument instead of picking a side.** Retail's
`UpdateOverlay` @0x82B87598 emits one `lwz r4, 0xNN(r31)` per overlay line, at
0x4 … 0x34: **fourteen** fields, so a field *does* exist at 0x34. Reading the
format string each call pairs with settles what they are:

| offset | retail format string | our field |
|---|---|---|
| 0x28 | `"multimesh %d\n"` @0x8219B79C | `mMultiMeshInsts` |
| 0x2c | `"flares %d\n"` @0x8219B790 | (we had `mMultiMeshBatches`) |
| 0x30 | `"motion blur %d\n"` @0x8219B780 | (we had `mFlares`) |
| 0x34 | `"spotlights %d\n"` @0x8219B770 | **we had no such field** |

Retail's 14th field is **`mSpotlights`, at the tail** — which is simultaneously
consistent with `EstimateDraw`'s twelve consecutive offsets (it does not use
`mSpotlights`, the last field) and with `UpdateOverlay`'s fourteen. **There was
never a contradiction between the two retail functions; there was a missing
field in the hypothesis.**

⚠ **The string probe was the thing that misled, and it was "negative" in
exactly the shape that reads as decisive.** `"multimesh batches"` really does
have zero occurrences — the probe was *correct* and *useless*, because it can
only say what is absent and is silent about what replaced it. Retail prints
`"multimesh %d"` (one line, different wording) and `"spotlights %d"`, each
present exactly once, and neither literal was in the probe. Count right, cause
wrong.

**Attempt 3, landed.** Drop `mMultiMeshBatches`, append `mSpotlights` at 0x34,
collapse the two multimesh overlay lines to one `"multimesh %d"` and add
`"spotlights %d"` after motion blur, in both the one- and two-column branches.
`"multimesh %d %d\n"`, `"multimesh %d\n"`, `"spotlights %d %d\n"` and
`"spotlights %d\n"` each occur exactly once in retail.

Predicted **+1 fn / +1,052 B** (`UpdateOverlay` crossing). **Measured Δ0 on
every key** — matched, masked_equal, honest, code%, fuzzy (+0.000000 pp) and
the `none` control (+0 B). **The prediction was wrong and this lane's own
classification already said so:** `UpdateOverlay`'s 14 charged sites are 14/14
`FOLD_TEMPLATE` — relocation-name charges against ICF-folded `MakeString`
instantiations — which no layout or format-string change can touch. Attempt 2's
−1,052 B is exactly cancelled by attempt 3's print fix, so the landed change is
neutral rather than negative, and it is right.

One inference was **checked and withdrawn before it was measured**: the obvious
place for retail to update `mSpotlights` is `SpotlightDrawer::DrawWorld`, but
retail's @0x824D7C18 opens straight on the `sLights`/`sCans` emptiness test
with no `NgStats` access at all. The running max stays a native-only static and
the real update site is an open question.

## 5. A map defect: `0x823c8908` is not `CharBlendBone::SetType`

`scripts/target_symbol_map.json` names `0x823c8908`
`?SetType@CharBlendBone@@UAAXVSymbol@@@Z`. The body there is
**`CharTransDraw::SetType`**. Three facts, any of which could have refuted it:

1. the body calls `?StaticClassName@CharTransDraw@@SA?AVSymbol@@XZ`
   (0x8236a928, itself mapped to CharTransDraw);
2. it uses virtual-base adjustor **0x3c**, and the compiler
   (`class_layout_report.py`) puts `CharTransDraw`'s vbase vfptr at **0x3c**
   and `CharBlendBone`'s at **0x34**;
3. retail's *own* `CharBlendBone::Save` @0x823C39D8 addresses `mTargets`,
   `mSrc1`, `mSrc2` and the four bools at vbase−0x2c/−0x20/−0x14/−0x8…−0x5,
   i.e. this+0x8/0x14/0x20/0x2c…0x2f with the vbase at **0x34** — every one of
   our offsets, exactly.

Two different vbase offsets means the two bodies **cannot** have been
ICF-folded, so this is a naming/homing error, not a fold. Geometrically it is a
**mis-homed pin**: `0x823C8908`–`0x823C8A64` is a standalone `.text` block
inside `CharBlendBone.cpp`'s `splits.txt` entry, its `.text` neighbours are
`Screenshot`/`RndDrawable` thunks, and `CharTransDraw.cpp` — which exists and
is declared `NonMatching` in `objects.json` — has **no `splits.txt` entry at
all**.

⚠ **Do not fix this by renaming the map row.** The target object for that block
is `CharBlendBone.obj`, and our `CharBlendBone.obj` does not define
`?SetType@CharTransDraw@@…`, so a rename alone makes the row permanently 0 %.
The fix is a splits **re-home** (give `CharTransDraw.cpp` its own entry and move
the block), which is not metric-neutral and needs a forced re-split on both A/B
legs. Left for a splits lane.

★ The generalisable point: this row reads as a clean, high-purity **struct**
bug — 12 of 13 charges are a uniform 8-byte member-offset delta — and it is
not a struct bug at all. A second retail function from the same class settled
it in one read.

## 6. Negatives, and what this lane did NOT do

- **Did not touch the 369 MIXED rows (228,928 B, 80.6 % of the tier).** Every
  one carries at least one register-only charge; the brief defers those to the
  permuter, and twelve recorded instances elsewhere in this campaign dissolved
  only after an unrelated source defect was fixed — so they are recorded, not
  deferred with a diagnosis.
- **Did not open the 31 ALIAS-BLOCKED rows (24,016 B).** Their charges are
  `FOLD_TEMPLATE` — `bl` to the same method of a different instantiation. The
  largest are `ShaderOptions::GenerateMacros` (3,084 B, 70/70 fold charges),
  `DataArraySongInfo::DataArraySongInfo` (2,496 B, 4/4: retail spells
  `vector<CharPollableSorter::Dep*>::reserve` where we spell `vector<float>` and
  `vector<int>` — all 4-byte element types, so the bodies genuinely fold),
  `NgRnd::UpdateOverlay` (1,052 B, 14/14) and `Geo::CheckBSPTree` (1,336 B,
  6/6). These need an **alias proof on retail bytes**, which is a different
  instrument from body work and an integrity hazard done casually.
- **Did not pursue the `_S_sort` cluster** — 11 rows / 4,712 B across Geo,
  Instance, CharBoneDir, CharClipSet, Rnd, UI, Utl, Mesh, Crowd, EventAnim,
  FileMerger, each with the *same* 4 symbol charges: retail loads the address
  of one ICF survivor (`RndMesh::Vert::operator delete`,
  `__destroy_aux<LocalePanel::Entry>`, …) where we load `~list<T>` for our own
  T. This is STLport `_S_sort`'s stack array of 64 lists whose element
  destructors fold across every 4-byte T. **One alias group would cover all
  eleven rows** — the best-concentrated alias target this lane saw, and the
  cheapest thing a follow-up could do.
- **Did not fix `Spotlight::DrawShowing`'s +0x10 member shift** (904 B) nor
  `RndEnviron::Save`'s layout (1,056 B, 204 sites). Both are single-class lanes.
- **Did not run a native driver.** The two landed changes touch a shader
  constant index and a debug-overlay struct; neither has a checked-in fixture.
  The native gate is the only native check taken (§8).
- **Did not verify that `ShaderMgr.h`'s other DC3-renumbered constants are
  right.** `kVS_RimColor`/`kPS_RimColor` were the only ones with a charged
  witness in this population; `kPS_BoxMapLight0`, `kPS_TexProcFrequency` and the
  rest are unaudited and are a plausible repeat of the same DC3 renumbering.
