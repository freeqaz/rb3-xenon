# W16-QP: the auto-only `auto_*` rows, grouped into components and classified by source (2026-10-06)

Lane W16-QP. Brief: W16-QM (`W16QM_SINGLE_OWNER_AUTO_ROWS_2026-10-06.md` §4) left
**1,568 in-scope `auto_*` rows / 440,300 B** whose only retail referencers are other
`auto_*` rows (QM's class `1unit-auto`). The tasks were:

- group them into call-graph components;
- identify each component's source TU from its strings, vtables/RTTI and callees;
- classify each component as source we hold (in `src/` or `../dc3-decomp/src`) or source nobody holds;
- pin and name the held ones whose bodies match retail, with a precision control as QM ran;
- record the rest by class and bytes.

Quazal and XDK were skipped. Worktree `~/tmp/wt-w16qp`, branch `w16-qp`, based on main
`1059a558f` (the W16-QM merge).

## 2. Components

The index is built from the live `build/45410914/asm/*.s`, keyed on `.fn fn_<addr>` and never
on the address column. Edges are `bl`/`b` targets and function-pointer relocations between
code rows.

Components come from union-find over auto→auto edges, with two rules. The first attempt
forced both:

1. **Hubs do not merge.** The first union produced a single 692 KB component, because
   `memset`/`memcpy`/`malloc`-class rows join everything that calls them. A row with more
   than 6 distinct callers counts as a hub, and an edge into a hub does not join the hub to
   its caller.
2. **Same gap only.** An edge joins two rows only when both sit in the same `auto_*` unit
   (one contiguous unpinned gap). A gap is one contiguous stretch of the link order, so it
   lies inside one library or a short run of TUs. A cross-gap edge is still kept as evidence
   about the callee, but it does not merge.

The result is 750 components, and every target row is in exactly one of them.

## 3. Identification

The evidence for each component was taken from retail bytes and the source trees, never from
the address column:

- map names already in `target_symbol_map.json` for any member.
- ASCII and UTF-16 strings the members load. Only distinctive strings were scored: those
  found in at most 4 files across `src/`, `../dc3-decomp/src` and `../rb3/src`. Common
  strings matched dozens of files and drowned the signal.
- RTTI for every vtable a member stores, read as vtable−4 → Complete Object Locator +12 →
  TypeDescriptor +8.
- the units of every callee and caller, and the two nearest pinned neighbours.
- the PE section. `BINK` is its own section.

Classes were then propagated in three ways:

- **`signal`**: the component has direct XDK evidence (Microsoft-mangled names, xdk callees,
  xdk strings).
- **`callgraph-r0` / `callgraph-r1`**: the component's only edges reach components that are
  already classified, so it takes their class.
- **`spatial`**: the component has no edges, and both of its nearest other-unit neighbours
  are under `xdk/`, so it is classed XDK.

**Spatial-rule control.** Over the pinned population, the rule "both nearest other-unit
neighbours are `xdk/` ⇒ this block is XDK" is right on **383 of 388 blocks (98.7%) and on
99.91% of bytes**. It was applied only where no other evidence existed, and it accounts for
176 rows / 33,144 B of X1.

## 4. Body matching, and why it found almost nothing

### 4.1 Global body matcher

Before relying on call-graph identification I tried the cheapest identifier: does any
compiled obj in the tree define a function whose body equals the retail body?

The matcher works in three steps:

1. Every in-scope obj function was indexed by `(size, md5 of the primary-opcode sequence)`.
2. Candidates were compared with relocated fields masked by opcode.
3. A callee check followed: where both our callee and retail's target have a known address,
   the two must agree.

**Acceptance rule ("strict"):** exactly one name anywhere in the tree (counting proven
aliases as one name) has a byte-equal body, and that name is not already mapped.

**Controls, run over rows whose owner is already known:**

| control | population | wrong | rate |
|---|---:|---:|---:|
| strict | 23,946 | 9 | **0.038%** |
| leave-own-unit-out (the owning unit's obj is hidden, as it is for an `auto_*` row) | 8,083 | 150 | **1.86%** |

Leave-own-unit-out error rate by stratum:

| stratum | wrong |
|---|---:|
| anonymous-namespace rows | 96% |
| plain rows ≤ 8 B | 22% |
| plain rows ≤ 16 B | 7% |
| plain rows ≤ 32 B | 3.9% |
| plain rows > 64 B | 0.39% |
| templates > 64 B | 1.2% |
| thunks > 64 B | 2.9% |

So small bodies do not identify a function, and neither do anonymous-namespace bodies.

The control exposed two defects in the instrument. Both were fixed before the result was read:

1. **Trailing padding.** 381 retail `.fn` extents (28 of them in `auto_*`) include one
   trailing `00000000` alignment word, so a byte-equal body never matched on size. The
   matcher now strips trailing zero words. The defect surfaced because
   `NoteTube::SetGlowLevel` (12 B) failed to match its own retail body.
2. **A contradicted callee was read as unknown.** When retail's callee was anonymous, the
   check passed even if *our* callee was mapped at a different retail address
   (`DiskErrorLoop` vs `SetDiskError` at `0x82516320`). A callee mapped elsewhere now counts
   as a contradiction. The strict rate above was measured after this fix.

**Result on the target rows: 1,464 rows / 437,316 B have no byte-equal body in any compiled
obj.** The strict rule accepted 3 rows. All 3 were then refused on evidence the matcher
cannot see:

- `??__FsCam`: W16-QI §5 shows this is a constant-initialized `ObjPtr<RndCam>` at
  `.data 0x82C707C4` with no readers.
- `MessageTimerDump`: it sits in the stagekit registration context, not in the `MessageTimer` TU.
- `json_object_object_get`: it is a UGCNet tail call.

**Precision on the target population is 0 of 3.** That outcome is expected: these rows are
missing from our objs because their source is missing, and §3 shows that directly.

### 4.2 Call-graph identification (NoteTube)

The only held component with compiled bodies is the NoteTube helpers. The near matcher
(difflib opcode similarity) only nominated candidates here. The identification itself is an
**exact call-graph isomorphism** against retail:

- `NoteTube::CreateMeshes` (pinned, `0x82C28F88`) calls
  `{InitializePlate ×2, DrawToPlate ×2}` in our source. Retail's `CreateMeshes` calls
  `0x82C29E98` at both `DrawToPlate` positions.
- `0x82C29E98` calls `{AllocateVerts ×3, AllocateFaces ×3, atan, tan,
  LookupPitchedUVCoordinates}`. That is exactly the set of calls our `DrawToPlate` makes,
  with the same counts. Its callees `0x82C29D88` (×3) and `0x82C294D8` are therefore
  `AllocateFaces` and `LookupPitchedUVCoordinates`.
- `VocalTrack::PrepareNoteTubes` (pinned) calls `0x82C294C8`, which our source spells
  `NoteTube::SetGlowLevel`.

QM's coverage rule holds: for each of the four addresses, every retail referencer is a pinned
row whose source names that callee at that position.

`0x82C294D8` and `0x82C29544` were one function that dtk mis-carved into two pieces (`0x6C` +
`0x5C`); neither piece has a `.pdata` record of its own. Once both pieces sat in the same
pinned unit, jeff's Class-4 over-carve merge rejoined them as one `0xC8` function. That is the
200 B our `LookupPitchedUVCoordinates` compiles to.

The pins went into `config/45410914/splits.txt` (unit `NoteTube.cpp`) and the names into
`scripts/target_symbol_map.json`:

| addr | name | B | after |
|---|---|---:|---|
| `0x82C294C8` | `NoteTube::SetGlowLevel` | 12 (16 with pad) | 100 |
| `0x82C294D8` | `NoteTube::LookupPitchedUVCoordinates` | 200 | 100 |
| `0x82C29D88` | `TubePlate::AllocateFaces` | 272 | 86.74 |
| `0x82C29E98` | `NoteTube::DrawToPlate` | 3,184 | 84.54 |

`SetGlowLevel` and `DrawToPlate` are not among QM's 1,568, because each has a pinned
referencer. They come from the same isomorphism and the same unit, so they are pinned with the
rest. The two partials (`AllocateFaces`, `DrawToPlate`) are body work for a later lane; this
lane is the first time they pair at all.

### 5.1 A tool conflict: `ab_measure --patch` cannot measure a pin that triggers a merge

The first A/B run was `--patch pins.patch` on the base commit, run
`20261006-144832-w16qp-notetube-62809`. It was **REFUSED at leg B's build**, and the cause
is a conflict between two guards:

- The pins make the split rewrite `symbols.txt` (the Class-4 merge).
- The split-guard (`[split-guard] THE SPLIT REWROTE ITS OWN INPUT`) therefore fails the ninja
  build with rc=1.
- `ab_measure` treats any failed build as a refusal. Its own iterate-to-fixed-point logic
  (lane ABSPLIT-1) never gets the chance to feed the rewritten `symbols.txt` back in.

So **a pin that triggers a `symbols.txt` rewrite cannot be measured with `--patch`.**
The workaround used here:

1. Commit the pins.
2. Run one build so the split writes the fixed point.
3. Commit `symbols.txt` on its own.
4. Measure with `--revert <pins commit>`. Both legs then carry the merged `symbols.txt`, and
   it is a fixed point for both.

The tree was restored correctly after the refusal. This is reported for the tool owners and
was not changed here.

⚠ A second trap from the same run: **`ab_measure`'s restore deletes untracked files created
while it runs.** This doc was first written into the worktree during the A/B and was removed
by the restore, which prints a banner saying so. Write deliverables to `~/tmp` during a run
and copy them in afterwards.

## 6. What was deliberately not done

- **No source was written.** `App::DrawRegular` (104 B, H2) has a dc3 body, but porting it
  would mean writing into a file whose draw path is unwritten. The FxSend360 stubs (H3) have
  no body to port in either tree.
- **No XDK, Quazal, Bink or liboggz work**, per the brief and the standing scope directive.
- **Nothing was named from the global matcher.** Its only three accepts were refused (§4.1).
- The near matcher was used only to nominate candidates, never to identify one.
- **No native gate.** The lane touches only `splits.txt`, `symbols.txt` and the map, with no
  `src/` change.
