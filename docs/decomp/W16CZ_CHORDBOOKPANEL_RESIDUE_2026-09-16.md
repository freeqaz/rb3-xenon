## 2. The two map corrections, and why they are safe

### `0x826a9f70` — `GetFretboardView` is `int`

Lane **INSDEL-3** (2026-08-14) left an in-source note deferring this row as codegen and
saying *"do not re-open"*. **Its diagnosis was right and its conclusion was scoped too
tightly**, and the note has been replaced in `GemTrainerPanel.cpp` with this record.
INSDEL-3 observed the surplus trailing `clrlwi r3,r11,24` is *"pure bool materialization"*
— which **is** the finding: a `bool` return *requires* that mask, retail emits none
(target 60 B vs our 64 B, exactly that instruction), so retail's return type is not `bool`.
INSDEL-3 held the signature fixed and only ever looked at this row. The discriminator is
at the **call site** it never examined: `PickFretboardView` tests the result with
`cmpwi r3, 0x0`, a full 32-bit test MSVC emits for `int` and never for a `bool` it must
harden. Two independent rows, two instruments, one answer.

The map's `_N` was never retail evidence: game map rows are generated by
`tools/gen_game_target_map.py` **from the rb3-Wii oracle**. No regression risk existed —
`?PickFretboardView@RGTrainerPanel@@...`, the other caller, has **no row in
`report.json` at all**, so it cannot lose points.

### `0x826ab108` — it is `~vector<GameGem>`, not `push_back<vector<Hmx::Color>>`

Prior lanes had already **proven the old name wrong without supplying the right one**:

- `docs/plans/wrong-callee-triage-2026-08-12.json` — `subclass: map_misassignment`,
  verdict *"our own definition of this callee scores 2.9% at `none` against the VA the map
  gives its name, so the map entry for OUR symbol is wrong and the charge is not evidence
  about the call site."*
- `docs/plans/comdat-fold-gate-2026-08-12.json` — **REFUSE**, *"our COMDAT is not the
  retail body at the survivor address -- body size 136 bytes (retail extent) vs 24"*.

The identity comes from retail bytes, five independent lines agreeing:

1. The body is destroy-range + `_M_deallocate(start, end_of_storage - start)`.
2. Its callee `fn_826AAEC8` is a backwards destructor loop stepping by **0x44** and
   calling the `GameGem` dtor fold survivor. `sizeof(GameGem)` = 0x44; `Hmx::Color` is 16.
3. The target's caller set — `GameGemList` (x3), `GemTrainerPanel`, `TrainerGemTab` (x2),
   `GameGemDB` — is **exactly** the set of our objects that define `~vector<GameGem>`.
4. Our `push_back<Color>` scored **2.91 fuzzy / 4.53 mpn** against it. A correct name
   does not score 2.91.
5. The extent `0x826AB0B4..0x826AB138` is 136 B, matching the row's `size` exactly.

**Cost: zero bytes.** The row lives in `default/ColorPalette` (pinned
`0x826AB01C-0x826AB358`), whose object does not define `~vector<GameGem>`, so the row goes
unpaired at 0.0 — but it was at 2.91, and `matched_code` is all-or-nothing on
`fuzzy == 100`, so nothing was being collected. The `splits.txt` pin looks wrong (the span
ends at `??4?$vector@VGameGem@@...`); **re-homing was NOT attempted** — re-homing an
already-pinned address is measured non-neutral, and the rename alone was sufficient.

Injectivity: both new names were verified absent beforehand. The map carries **2
pre-existing duplicate names** (`?NodeCmp@@YAHPBX0@Z`,
`??$__destroy_aux@ULevelData@@...`) — present identically in `HEAD`, **not introduced by
this lane** — and the build gate reports one as *"not applied (denylisted/null), so not a
finding"*.

## 3. Rows left open, with diagnoses (all permuter-class; permuter is OFF by directive)

### `?DisplayChord@ChordbookPanel@@QAAXI@Z` — 3,436 B @ fuzzy 97.1793
90 mismatches: **44 register swaps dominated by r14<->r15 (30 of 44)**, 25 address-relocation
noise, 2 branch-polarity, 4 commutative, plus real code motion (the `mulli r11, r28, 0x4c`
`ChordInfo` indexing is emitted at a different point: deletes at idx 39-43, inserts at
105-106). The biggest prize in the unit and not reachable without the permuter.
**Its `OFFSET_SWAP (0x54,0x58)` rows are a mislabel** — see §4.

### `?SetFret@ChordbookPanel@@QAAXHH@Z` — 716 B @ fuzzy 99.88827, `mpn` 100
Exactly two charges, both in `SetCorrect` **inlined** into `SetFret`:
```
95  lbz  r9, 0x698(r30)     ; r9  = mCorrect
97  slw  r10, r25, r26      ; r10 = mask
98  and  r8,  r10, r9  |  and  r8,  r9, r10   <- target puts mask first
108 or   r10, r10, r9  |  or   r10, r9, r10   <- target puts mask first
110 andc r10, r9,  r10 |  andc r10, r9, r10   <- EQUAL; non-commutative, so it PINS the roles
```
**Two levers tested, both dead.** (a) Source operand order: wave A spelled both ops in
retail's order (`mask & mCorrect`, `mask | mCorrect`) and measured **Delta 0**, with the
recompile confirmed in the build log and the instruction confirmed not to flip — MSVC
canonicalises commutative integer operands regardless of source spelling. (b) Production
order: the listing shows it is **already identical** on both sides, so no source edit can
reach it. `at_limit` for source work; needs the permuter.

### `?HandleLegendLefty@ChordbookPanel@@QAAX_N@Z` — 316 B @ fuzzy 89.4937
Target **316 B vs our 292 B**: retail materialises the `1.0f`/`0.0f` constant-pool loads
**in both arms** (idx 29-34 are 6 target-only instructions) and branches *before* them;
MSVC CSEs them for us into one copy *above* the branch (our `beq` lands at idx 25, retail's
at 18). Everything else in the function is equal. This is a CSE/scheduling decision with no
source token behind it. The prior `DECOMP_FORCEACTIVE` lead is **refuted** — see §4.

## 4. Coordinator-brief claims found WRONG

1. **§3 "`fn_826B7BA0` not identified"** — it is `?HasChords@ChordbookPanel@@QBA_NXZ`,
   now installed and at 100.0. The brief's "stride 0x44 doesn't match `ChordInfo` (0x4C)"
   worry dissolves once `fn_826B7AF8` is seen to be `vector<GameGem>`'s copy ctor: 0x44 is
   `sizeof(GameGem)`.
2. **§5 is wrong about `SetFret`.** Its penalties are **not** relocation-name charges; they
   are commutative-operand **register** swaps. The inference *"`mpn == 100` ⇒ every penalty
   is a relocation-NAME charge"* is invalid, because `mpn` excludes **all** non-immediate
   arg diffs, register operands included.
3. **§4's `OFFSET_SWAP (0x54,0x58)` is not a struct defect.** The base register is **r31**
   (frame pointer), not `this` (r30); `stack-layout` names them as the `int` locals. The
   compiler's own `/d1reportSingleClassLayout` confirms `mChordLegend`=0x54 and
   `mGameGemList`=0x58 are correct. objdiff's offset resolver mislabels stack slots as
   `this`-relative fields, and it still does so in `DisplayChord`.
4. **§6's `DECOMP_FORCEACTIVE` lead is refuted.** The rb3-Wii oracle carries
   `"lefty_flip.anim"` in its forceactive precisely because it has **no
   `HandleLegendLefty` at all**; ours does, and already references that string in real code.
   The 24 B shortfall is the constant-materialisation difference in §3.
5. **objdiff's `COMMUTATIVE_OP_ORDER (LikelyFixable)` is measured wrong on `SetFret`** —
   source operand order is inert (wave A, Delta 0).

  wrong: re-homing an already-pinned address is measured non-neutral, and the rename alone
  bought the bytes. Flagged for a pinning lane.
