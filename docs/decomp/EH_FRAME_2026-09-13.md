# W12-A — the surplus EH state, and what "it is a CLASS" actually turned out to mean

**Lane:** W12-A · **Branch:** `w12-eh-frame` · **Base:** `96c3a685` · **2026-09-13**

Follow-on to W11-C (`docs/decomp/CTOR_INLINE_SWEEP_2026-09-13.md`, merge
`c0b47e9f`), executing its handoff #1: the EH-frame wall behind
`??0RndPartLauncher@@IAA@XZ`, which W11-C believed was shared with
`??0Anim@EventTrigger@@QAA@PAVObject@Hmx@@@Z` and suspected was a class.

**Headline:** the wall is real, its cause is now known exactly, and it is fixed.
But **two of the brief's premises are refuted**: the second row is a *different
defect*, and the class — which does exist, and is now measurable for the first
time — is a **diagnostic** class with per-row causes, not a single lever.

---

## 1. Refutation first: `EventTrigger::Anim` is not this defect

`target_size 188 == base_size 188`. There is no frame growth, no displacement,
and no surplus state store. `stw r3,0x94(r31)` (the `this` home store W11-C read
as ours-only in PartLauncher) is present **on both sides** here, at index 5, and
both sides carry exactly one `stw r29,0x50(r31)` at index 26, equal.

Its entire defect is **one store scheduled two slots early**: we emit
`stw r4,0x4(r3)` at index 6, retail at index 8, after `lis r10,<vtable>`. Two
charges over 47 instructions = **95.74468%**, which is the row's score to the
digit.

⇒ The 516 B figure in W11-C's handoff is **not collectable by one fix**. 328 B of
it is this lane's; the other 188 B is an instruction-scheduling row that shares
nothing with it but a neighbouring lane number.

## 2. What the surplus store actually is — the compiler's own words

W11-C read the residual as "one surplus EH-state store". That is the right
*shape* and the wrong *noun*, and the difference matters because it points at a
completely different fix. `/FAs` on the TU names every frame slot:

```
$T55832 = 80    ; 0x50  size = 4
$T55904 = 84    ; 0x54
$T55899 = 84
$T55861 = 84      <- four member cleanup temps, all coalesced onto ONE slot
$T55880 = 84
this$   = 148   ; 0x94
```

and the funclet says what `$T55832` is for:

```
__unwind$55833:  lwz r11,$T55832(r31); clrlwi. r11,r11,31   ; test bit 0
                 beq $LN11
                 lwz r11,$T55832(r31); clrrwi r11,r11,1     ; clear bit 0
                 lwz r11,this$(r31); addi r3,r11,0xB8
                 bl ??1Object@Hmx@@UAA@XZ                   ; destruct the VIRTUAL BASE
```

`0x50` is the **virtual-base-constructed flag**, not an EH state counter.
`RndPartLauncher` virtually inherits `Hmx::Object` (hence `??_8RndPartLauncher@@7B@`
and the `cmplwi cr6,r4,0` most-derived guard), and `li r11,1; stw r11,0x50(r31)`
is `flag |= 1`. The four `0x54` stores are the member cleanup pointers, which are
displaced only *because* the flag needs its own slot.

## 3. The contradiction that forced me to read retail's EH metadata

Retail's funclet at `fn_8244FE90` is **byte-identical to ours** — it reads the
flag at `0x50` and `this` at `0x94`. But retail's mainline (`fn_8244FD48`, raw
split bytes, not objdiff's view) writes **neither**, and reuses `0x50` for the
four member pointers. A funclet cannot read a slot its parent never writes, so
either the row was misidentified or my model was wrong.

It was my model. Parsing retail's own `FuncInfo` out of `band.exe` settles it:

| | retail (`fn_8244FD48`) | ours |
|---|---|---|
| `maxState` | **6** | **7** |
| unwind map | vbase, then 5 member states | + a 7th: `ObjPtr<RndMesh>` (this+0x20) |
| IP-to-state entries | **1**, at `0x8244fe8c` = *one past the end* | **2** |
| state at `bl ??0PartOverride@@QAA@XZ` | **−1 (unprotected)** | **6** |

Retail's single IP2State entry sits past the last instruction, so **every IP in
retail's ctor body resolves to state −1**: retail protects nothing, which is why
the flag and the `this` home are dead stores there and get eliminated (and the
flag slot then coalesces with the temps). The funclets survive as unreachable
metadata — which is exactly why retail *appears* to read slots it never writes.

⇒ **Root cause: retail's compiler knew `PartOverride::PartOverride()` could not
throw. Ours did not.** It is the only call in the ctor body, and every other
difference follows from that one fact.

## 4. The fix, and why it is not metric-fitting

`PartOverride::PartOverride()` is declared in `rndobj/Part.h` and defined in
`Part.cpp`, so it reaches our TU as `EXTRN` and the compiler must assume it
throws.

**The DC3 oracle already spells it `throw()`** —
`dc3-decomp/src/system/rndobj/Part.h:85` and `Part.cpp:65`. Same Milo engine,
same compiler build, same `/O1 /Oi /GR /EHsc` flags, arrived at independently.
DC3 even carries a comment on the general mechanism (in `xdk/nuiapi/headtracker.cpp`):
*"throw() is load-bearing, not decoration"*, with a **binary** evidence standard
(the target obj's EH symbols), not a metric one. So this is restoring a spelling
our port dropped, corroborated by retail's own EH metadata — not a knob tuned
until the number moved. rb3-Wii has plain `PartOverride()`, but MWCC has no such
codegen behaviour and rb3-Wii is a dev build.

**Pre-registered prediction, before any build:** with the callee declared
nothrow the ctor loses all three surplus instructions, the temps move
`0x54 -> 0x50`, size goes `340 -> 328`, and `maxState` drops `7 -> 6`.

**Single-TU `/FAs` probe, all five points hit:**

| | baseline | nothrow | retail |
|---|---|---|---|
| `stw r3,this$` | present | **gone** | absent |
| `li r11,1; stw r11,$T` | present | **gone** | absent |
| temp slots | `= 84` (0x54) | **all `= 80`** | 0x50 |
| `maxState` | `07H` | **`06H`** | 6 |

The probe also reproduced retail's apparent anomaly — the nothrow build's
funclets still read `this$` at `0x94` while the mainline never writes it. That
confirmed the "misidentified row" hypothesis was wrong and that this is ordinary
MSVC dead-store elimination which does not account for funclet reads.

## 6. Is it a class? A new instrument, and a bounded answer

The brief asked me to screen for "a +12 B frame and EH temps displaced by 4".
**That symptom under-counts by construction**: a surplus EH state only costs
mainline bytes when it happens to force a flag store or a slot split. For a
class without a virtual base there is no flag, and the surplus can be invisible
in the mainline while still charging the row.

So I screened the **mechanism** instead: `FuncInfo.maxState`, retail vs ours,
whole-tree. `tools/eh_state_screen.py` (landed with this lane) reads

- **retail**: the 8-byte EH prefix dtk renders as `.obj except_data_*`
  immediately before each `.fn`, whose second word is the `FuncInfo` VA; then
  `maxState` at +4 out of `band.exe`'s `.rdata`, big-endian;
- **ours**: the COFF symbol `__ehfuncinfo$<mangled>` in each compiled `.obj`;

joined by mangled name through `scripts/target_symbol_map.json`.

**Validation, both of which could have failed:** the known-answer fixture
`??0RndPartLauncher@@IAA@XZ` reads **retail=6 / ours=7** through the full join
path, and the instrument **discriminates** rather than firing on everything —
4,155 joined, **153 disagree**.

| | count |
|---|---:|
| retail EH-bearing functions found in the split `.s` | 7,024 |
| our `__ehfuncinfo$` symbols | 10,598 |
| joined (mangled name known on both sides) | **4,155** |
| disagree | 153 |
| — **ours > retail (surplus: this class)** | **54** |
| — ours < retail (the opposite defect) | 99 |

⚠ **Coverage bound, stated so nobody reads 54 as complete:** 2,554 retail
EH-bearing addresses are absent from the map, so the screen sees roughly **59%**
of retail's EH functions. 54 is a floor on the class, not its size.

### The class is real but it is NOT one lever

Surplus deltas run +1 to +9. Sub-classifying by retail's IP-to-state entry
count — where `nIPMap == 1` means *retail protects nothing*, PartLauncher's
distinctive shape — gives 16 of the 54. But **15 of those 16 have retail
`maxState == 1`**, i.e. retail has one trivial unwind state; PartLauncher is the
**only** row in the tree with real retail cleanup states *and* an unprotected
body.

Spot-checking three other `+1` ctors on retail's own data shows they are **not**
PartLauncher's shape: `??0Sfx@@IAA@XZ` has 3 IP2State entries, `??0RndGroup@@IAA@XZ`
4, `??0RndFlare@@IAA@XZ` 3 — retail *does* protect regions in all three, so their
surplus state has a different cause and will need its own callee identified.

⇒ **The honest verdict: "our EH state count exceeds retail's" is a real,
bounded, newly-measurable defect class of at least 54 rows — but it is a
DIAGNOSTIC class with per-row causes, not a single fix.** W11-C's instinct that
the wall generalises was right about the *phenomenon* and wrong about the
*remedy*.

## 7. A bounded negative: DC3's second `throw()` does not transfer

DC3 carries exactly three non-STL `throw()` sites: `PartOverride` (ours, fixed),
`LDARegressor` and `SynapseAPOParams`. Checked, not assumed:

- **`LDARegressor`** lives in `src/xdk/nuiapi/headtracker.cpp`, which is **not in
  our `objects.json`** — not compiled here. Out of scope (XDK) and worth nothing.
- **`SynapseAPOParams`** (`src/system/synth_xbox/FxSendSynapse.{h,cpp}`) **is**
  compiled, and DC3 spells it `throw()` while we do not — but **no function in
  our tree that constructs one shows a `maxState` surplus**. Following DC3's own
  discipline (*"an exception specification that buys no codegen is semantic
  surface for free"*), I did **not** add it.

⇒ Copying the oracle's `throw()` sites wholesale would have been wrong. Two of
three buy nothing here.

## 9. What I deliberately did NOT do

- **`??0Anim@EventTrigger@@`, 188 B, left at 95.74.** Characterised exactly
  (§1) rather than ground: its residual is a single store scheduled two slots
  early, which is scheduler behaviour, and the permuter is off by directive. It
  is *not* an EH row and should not be briefed as one again.
- **`SynapseAPOParams` `throw()`** — DC3 has it, we do not, and it buys nothing
  here (§7). Not added.
- **`LDARegressor`** — `src/xdk/`, not compiled here, out of scope.
- **The other 53 surplus-EH rows.** Screened, sub-classified and ranked; none
  fixed. Three were checked against retail's IP2State data and are demonstrably
  a different shape from PartLauncher.
- **The 99 `ours < retail` rows** — the opposite defect (retail protects more
  than we do). Surfaced by the same instrument, not investigated at all.
- **No map, splits or alias edits**; `scripts/symbol_aliases.json` untouched. No
  permuter. The ceiling, the `auto_*` class and the obj-patcher census were not
  re-measured; nothing here depends on them.

## 10. Handoffs

1. **`tools/eh_state_screen.py` is the reusable asset, not the 328 B.** It is
   the first instrument in the tree that compares C++ EH *semantics* between
   retail and our build. Re-run it after any wave; its failure mode is
   checkable (known-answer fixture + it must not fire on everything).
2. **Raise the screen's coverage.** It joins only 4,155 of retail's 7,024
   EH-bearing functions because 2,554 retail EH addresses are unmapped. Every
   identification wave widens this screen for free.
3. **The 99-row `ours < retail` direction is untouched and may be the richer
   vein** — those are functions where retail emits EH machinery we do not, which
   is the shape that costs *retail-side* instructions we fail to emit.
4. **Method worth reusing: when a funclet reads a frame slot its parent never
   writes, stop inferring and parse `FuncInfo`.** That contradiction is what
   turned this row from "an EH-frame wall" into a one-word source fix. The
   8-byte EH prefix is rendered in the split `.s` as `.obj except_data_*`; its
   second word is the `FuncInfo` VA in `band.exe`'s big-endian `.rdata`.
5. **`throw()` is a legitimate, oracle-backed lever — but site by site.** Two of
   DC3's three sites buy nothing here. Require a `maxState` surplus *and* a
   retail-side IP2State gap before adding one.
