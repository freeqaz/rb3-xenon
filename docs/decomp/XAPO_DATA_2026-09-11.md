## 2. `.data` pinning: the 13.4 kB is not in the denominator at all

### 2.1 The brief's framing does not survive contact

The brief asked whether "adding a pin over previously-unpinned `auto_*` code is
metric-neutral" transfers from `.text` to `.data`. It does not transfer, and the
reason is **stronger than neutrality — data sections cannot move a code measure
at all.** From objdiff's own report generator (`objdiff-cli/src/cmd/report.rs`,
the section loop):

```rust
match section.kind {
    SectionKind::Data | SectionKind::Bss => {
        measures.total_data += section.size;
        if section_match_percent == 100.0 { measures.matched_data += section.size; }
        continue;                    // <-- SKIPS THE PER-SYMBOL LOOP ENTIRELY
    }
    _ => {}
}
```

The `continue` is the whole story. `matched_code`, `total_code`,
`matched_functions`, `masked_equal_functions` and `fuzzy_match_percent` are all
accumulated **inside** the per-symbol loop that this arm skips. A data section
therefore contributes **no rows** and touches **no code measure**, by
construction.

Corroborated three ways rather than read once:

* `report.json` has **69,219 rows and ZERO** whose name begins `??_7` (vtable),
  `??_R` (RTTI) or `??_C` (string literal) — the data-symbol classes. That
  absence is the `continue` observed from outside.
* `.rdata` is in the same bucket: `objdiff-core/src/obj/read.rs` maps
  `ReadOnlyData`/`ReadOnlyString`/`Tls` → `SectionKind::Data`. So **no**
  non-code section is scored, not just `.data`.
* Whole-binary `matched_data` is **absent from the `measures` block**, i.e. 0
  (protobuf-JSON omits defaults), against `total_data` **4,156,972**. Not one
  byte of data is matched anywhere in this binary today.

### 2.2 Measured, not merely argued

Pinned exactly one regProps object — `GainEffect.cpp`, `.data
0x82CA74C8..0x82CA78F8` — and A/B'd it.

Predicted Δmatched **+0**, Δcode_bytes **+0**, Δcode% **+0.000000pp**.
Measured **+0 / +0 B / +0.000000pp**, Δfuzzy **+0.000000pp**, units at 100%
unchanged on both rulers. The pin was then **reverted**; see §2.4.

### 2.3 Two traps a future lane will hit, both measured here

⛔ **Pin `.data` to dtk's symbol extent, NOT to `sizeof`.** The first attempt
pinned `0x82CA74C8..0x82CA78F4` — exactly `sizeof(XAPO_REGISTRATION_PROPERTIES)`
= `0x42c` = 1068, which is the right answer about C and the wrong answer about
dtk. The split **refused**:

```
Failed: Split GainEffect.cpp .data (0x82CA74C8..0x82CA78F4)
        ends within symbol 'lbl_82CA74C8' (0x82CA74C8..0x82CA78F8)
```

dtk infers data-symbol extents **alignment-rounded** — `0x430`, four bytes more.
A `.data` pin must name dtk's extent.

⚠ **And that 4-byte rounding makes the section score 89.597% even though the
content is PERFECT.** With the pin accepted, `default/GainEffect`'s `.data`
section reads `fuzzy=89.597`, which looks exactly like a content defect. It is
not. Compared our compiled `?m_regProps@?$CSampleXAPOBase@VGainEffect...`
COMDAT against retail `0x82CA74C8` byte-for-byte:

```
our COMDAT .data size=1068   retail carved extent 0x430=1072
differing bytes in common prefix: 0
retail tail beyond ours: 00 00 00 00
```

**1068 of 1068 identical; the residue is four bytes of padding dtk added.** So
the answer to the brief's byte-content question is *yes, the static half matches
exactly* — CLSID `B4D4C8AA-A20D-40A1-84A7-641935 51A9BC` then BE-UTF16
`L"SampleAPO"` at `0x10..0x21`, then zeros through `0x42b`, precisely the region
the initialiser's `memset(obj+0x24, 0, 0x1ec)` skips (W5-B §2, confirmed
independently here).

### 2.4 Verdict: do not pin `.data` for these TUs

It is inert on every scored measure; it cannot reach `matched_data` either
(that needs the **whole** section at 100%, and dtk's carve is 4 bytes longer
than our COMDAT); and a pinned section reading 89.597% invites a future reader
to hunt a content bug that does not exist. Documented rather than pinned. The
13 × 0x42c stays in `auto_06_82C64400_data`, and **that costs nothing** — it was
never in `total_code`.

### 3.3 The identification instrument: `.text$yc` order mirrors `.text` order

Linker section ordering puts `.text$mn` before `.text$yc`, and within each group
preserves object order — so a TU's initialiser sits at the same *rank* as its
main code. Verified monotonic across **20 anchors** (W5-B's twelve regProps
owners plus Voice, ExternalMic, and SynapseAPO):

```
block1(16) < Synth 82B59F78 < Distortion 82B61488 < Delay 82B61C40
  < Chorus 82B62450 < EQ 82B630C0 < Wah 82B64298 < Voice 82B64C20 (8 rows)
  < [five 12-byte tails] < MeterEffect 82B6B4F0 < ... < SynapseAPO 82B6DA40
```

Both columns ascend without exception. This is a reusable instrument: it turns
"which TU owns this initialiser" into a bounded interval question.

### 3.4 The five tails are ExternalMic.cpp — four agreeing channels

1. **Count + size.** `ExternalMic.obj` emits exactly five 12-byte `??__E`
   COMDATs in `.text$yc`; retail has exactly five 12-byte bodies here.
2. **Link order.** ExternalMic.cpp's `.text` is `0x82B66C50`, between Voice and
   MeterEffect; it had **no** `.text$yc` pin, and this is the only unclaimed
   `.text$yc` slot in its window.
3. **Object identity.** Each row's registered thunk
   (`0x82C4B868/898/8C8/8F8/928`) destroys one of five consecutive 12-byte
   vectors at `0x82E1218C/98/A4/B0/BC` (`vector` = start/finish/end = 12 B).
4. **Retail's own use.** `fn_82B66D68` does `[0x82E121A4][dev] = master` and
   `[0x82E121B0][master] = dev`, so `A4` is `mDevToMicMaster` and `B0` is
   `mMicMasterToDev`; `0x82E1218C` is iterated by `(finish-start)>>2` (`gMics`),
   `98` yields a proxy pointer (`mMicMasters`), `BC` stores a pointer
   (`mAssocMicXbox`).

Channel 4 fixes the permutation to **source-declaration order**, which equals
our `.text$yc` COMDAT order.

⛔ **NEGATIVE WORTH KEEPING: our `.bss` order is a DIFFERENT permutation and
would have mis-assigned 3 of 5.** `ExternalMic.obj`'s `.bss` lays the five out
as `gMics(+0x18), mMicMasters(+0x24), mMicMasterToDev(+0x30),
mAssocMicXbox(+0x3C), mDevToMicMaster(+0x48)` — MSVC does **not** order `.bss`
and `.text$yc` alike. The obvious "both sides are the same compiler, so use our
object layout as the oracle" shortcut is wrong here. Only retail's own use of
the objects settled it.

### 3.5 Naming was NECESSARY, not cosmetic

W5-B's thirteen had no downside channel (zero `bl` callers), and these five have
none either — their only references are CRT-init-table `.4byte` entries in the
unpinned `auto_06_82C64400_data` unit. But unlike W5-B's case, **a bare re-home
would not have paid**, and the reason is a pairing hazard rather than a scoring
one:

`ExternalMic.obj` carries ~6 `_M_throw_length_error` / `_M_throw_out_of_range`
stubs whose masked byte signature is `3d600000 386b0000 4bfffff8` — **identical
to the `??__E`**. The funclet byte-signature fallback assigns arbitrarily within
a signature group, so a target `??__E` could pair against a thrower and keep the
`b atexit` vs `b ?__stl_throw_length_error` charge. Names force the correct
pairing.

That charge is exactly what was costing the 60 bytes. In Voice the five were
mispaired against Voice's `??__F` **destructor** thunks:

```
| 0 | lis r11, fn_82C4B868@h | lis r11, ?gInProgressSyncVoices@@3V?$list@PAVVoice@@...@h |          |
| 1 | addi r3, r11, ...@l    | addi r3, r11, ...@l                                      |          |
| 2 | b atexit               | b ?clear@?$_List_base@PAVVoice@@...@@QAAXXZ              | diff_arg |
```

One charged site, `fuzzy 98.333`. All five spellings were lifted **verbatim**
from `ExternalMic.obj`'s symbol table (never typed), all five are already `sc=2`

`?A0x0298b308` is **retail's** — the map already carries it for
`?ExternalMicThreadEntry@?A0x0298b308@@YAKPAX@Z` at `0x82b677c0`.

## 4. BitCrush: retail has none, and the phantom was hiding a real bug

W5-B labelled `BitCrushEffect`'s uuid DC3-inherited and unverifiable, and
flagged as "the useful signal" that retail's `FxSendBitCrush360::CreateFx`
likely differs from ours. Adjudicated on retail bytes. The answer is not
"differs".

### 4.1 Retail contains no BitCrush whatsoever

* The literal byte string `BitCrush` occurs **ZERO** times in `band.exe`, in any
  case (`BitCrush`/`bitcrush`/`BITCRUSH`/`bit_crush`). Scanned in Python. ⚠ The
  shell's `grep` is binary-blind and returns this same answer **vacuously** —
  a decisive-looking negative that proves nothing. This is precisely the vein
  CLAUDE.md warns closes silently.
* Retail carries RTTI type names for **eleven** `FxSend*360` classes — Chorus,
  Compress, Delay, Distortion, EQ, Flanger, MeterEffect, PitchShift, Reverb,
  Synapse, Wah — and for every matching non-360 base. Neither
  `.?AVFxSendBitCrush360@@` nor `.?AVFxSendBitCrush@@` exists. **Every sibling is
  present and this one alone is absent**; that asymmetry is the finding, and it
  is what makes the zero-occurrence count meaningful rather than vacuous.

⇒ `FxSendBitCrush360::CreateFx` has **no retail counterpart to differ from**,
which is why `src/system/synth_xbox/FxSendBitCrush.cpp` is compiled but has
never been pinned and owns no map name. The uuid stays unverifiable and stays
labelled in-source; it is metric-irrelevant, exactly as W5-B said.

### 4.2 …and `system/synth/FxSendBitCrush.cpp` was a PHANTOM UNIT

The heading pinned two ranges belonging to other TUs, and the map named three
addresses in a three-way cross-assignment. Adjudicated by **vtable + RTTI
Complete Object Locator** — the instrument that settles this. (Raw byte
comparison is dead here: PC-relative displacements differ at different
addresses, so it finds each body "unique" and proves nothing.)

| addr | vtable slot | map said | truth |
|---|---|---|---|
| `0x82712CA0` | FxSendPitchShift `[9]` | `?Copy@FxSendBitCrush@@` | `?Copy@FxSendPitchShift@@` |
| `0x82721400` | FxSendDistortion `[9]` | `?Copy@FxSendPitchShift@@` | `?Copy@FxSendDistortion@@` |
| `0x82721370` | FxSendDistortion `[10]` | `?Load@FxSendBitCrush@@` | `?Load@FxSendDistortion@@` |

**Slot labelling has a control**, which is what makes this safe: PitchShift's
`vtable[10]` is independently and *correctly* map-named
`?Load@FxSendPitchShift@@`, fixing slot 10 = `Load`; and two independent
vtables put a `Copy` name at slot 9. Once carved correctly the two clusters are
clean — `0x82712C28–0x827130B0` holds every FxSendPitchShift virtual,
`0x827212E8–0x82721718` every FxSendDistortion one. (`0x82712FB0`
`?Save@FxSendDistortion@@` appears in **both** vtables — a genuine ICF fold,
deliberately left alone.)

### 4.3 The −144 B is the point

* All three `Copy` bodies are **relocation-normalised IDENTICAL** (104 B,
  `norm 75e2329a1717`) across PitchShift/Distortion/BitCrush ⇒ both `Copy`
  renames are byte-neutral **by construction**, not by hope.
* The `Load` rename is not. Our `?Load@FxSendDistortion@@` is **152 B** where
  retail's body at `0x82721370` is **144 B**, and our DC3-inherited
  `?Load@FxSendBitCrush@@` is **byte-exactly** retail's Distortion `Load`.
  ⇒ **our `FxSendDistortion::Load` is wrong**, and the misnamed row was holding
  it at a false 100%.

⚠ **The +8 was not accepted on its face** — that is exactly the STLPORT-1
artifact shape, where a next-symbol delimiter bills the successor's 8-byte EH
prefix into a COMDAT span. Checked the tail: `38 3f 00 a0 48 00 00 00` =
`addi r1, r31, 0xa0` plus a relocated branch, i.e. **real epilogue code, not two
pointers**. The delta is genuine.

Rename safety was checked rather than assumed (W9's hard limit: a destination
obj that cannot define the name sends the row **permanently** to 0%). All three
names are DEFINED in their destination objects — and the check had to
distinguish a definition from an external reference, because
`synth_xbox/FxSendDistortion.obj` carries both names as **UNDEFINED refs** and a
name-presence test passes on them.

`.pdata` was left to dtk per the standing contract that it is derived output.
The first build failed the split-guard **by design** and re-derived it; every
re-derived range landed in the unit this carve predicts, which is independent
corroboration of the carve. Target objects **3085 → 3084** — the phantom unit
vanishes with no COFF hard-fail, and the full build passes.
