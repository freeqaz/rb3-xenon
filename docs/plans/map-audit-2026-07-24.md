# target_symbol_map.json — whole-map mispair audit (2026-07-24)

Generalizes the BinDiff-r2 mispair method (commit bbad6464) over the **entire**
`scripts/target_symbol_map.json` (19,947 address→mangled entries). Read-only;
verdicts here, coordinator lands.

## Method

- **`.pdata` is the function-entry authority.** Parsed the X360 `.pdata`
  (57,733 `RUNTIME_FUNCTION` entries) from `orig/45410914/band.exe` (= current
  TU5 target, byte-identical to Ghidra `default_tu5.xex-c5a170`). Decoded each
  entry's exact `FunctionLength = ((word1>>8) & 0x3FFFFF) * 4`, giving true
  function extents (not just start deltas).
- A map VA is classified **PDATA** (is a function start), **FRAGMENT** (falls
  strictly *inside* a pdata function's body → cannot be a function start →
  systematic mispair), or **GAPLEAF** (in a gap after a pdata fn end → a
  candidate leaf-function start; leaf getters/imports legitimately have no
  `.pdata`).
- Strict status from `build/45410914/report.json`
  (`match_percent_normalized==100`). Strict entries are byte-proven → skipped.
- Compiler-helper stubs (`__savefpr_*`/`__restfpr_*`…) and vtordisp/adjustor
  thunks (`@@$4…`) / EH funclets legitimately live at non-pdata addresses →
  classified, not flagged.

**Key validation of the model:** 1,981 map entries are GAPLEAF **and
strict-100** — i.e. real leaf functions with no `.pdata` that already match
byte-for-byte. This proves non-pdata ≠ mispair; only *FRAGMENT* (inside a body)
is a reliable mispair signal. Independently Ghidra-confirmed on KickPlayer
(below).

## Verdicts — 293 mispairs, all DELETE (high/med confidence)

| verdict | count | meaning |
|---|---:|---|
| DELETE-MISPAIR-DORMANT | 178 | fragment; name absent from report.json (no obj compiles it) → dead mislabel, zero-risk delete |
| DELETE-DUP | 113 | fragment; name is a duplicate whose real home is a sibling PDATA/GAPLEAF entry (the sibling carries any strict match) |
| DELETE-DUP (adjacent-leaf) | 2 | AllowsPartialHits / Sine — VA points at a padding word / prev-fn `blr`; real fn is the adjacent sibling |

No REPOINT candidates were required: every FRAGMENT mispair's name either (a) has
its correct home already present as a sibling map entry (DELETE-DUP), or (b) is
dormant (no compiled obj → nothing to repoint). **None suppress a live strict
match** — the strict match, where it exists, lives on the correct sibling VA, so
deleting the fragment copy only removes an ambiguous duplicate label (protects
the match on rebuild). This mirrors the r2 sweep's finding that these old-pass
entries point at leaf/fragment addresses.

Full per-entry list: `~/tmp/map_audit_verdicts.json`
(fields: va, mangled, bucket, verdict, evidence, confidence).

## KickPlayer lead — adjudicated

`?KickPlayer@SessionUsersProvider@@QAAXH@Z` duplicate:
- **`0x826542b0` — KEEP.** PDATA start (len 116). Ghidra decompiles it as the
  real KickPlayer (reads the user list at `+0x2c`, calls the kick routine).
- **`0x826377e8` — DELETE.** FRAGMENT, +8 bytes into `0x826377e0`, which Ghidra
  decompiles as an unrelated `FindObject`/`RTDynamicCast`/`PathName` function.
  Classic mispair. (Captured in verdicts as DELETE-DUP.)

## Secondary vein — 117 "ambiguous" duplicate names (both VAs non-fragment)

Same mangled name at two *real* (non-fragment) VAs — the `.pdata` method's blind
spot (a mispair landing inside a **leaf** function has no pdata extent to detect).
Split by address adjacency:
- **107 far-apart** (>128 B / different units): overwhelmingly STL template /
  ICF-unfolded instantiations (`??$sort@…SongRankCmp@@`, `??$__destroy_range_aux@…`,
  AccomplishmentProgress getter clusters). Low harm (mostly best_pct 100 on one
  copy); adjudicating requires per-entry oracle. **Deferred vein**, listed in

- **10 adjacent** (<128 B): 2 resolved to clean DELETEs above (padding/blr
  sibling); the other 8 have both VAs starting with valid prologues
  (`7d8802a6` mflr) = genuine unfolded twins, benign. See
  `~/tmp/adjacent_dup_verdicts.json`.
