recurse=true)` descends only through `mSubDirs`. A `Character` **is** an

crowd characters — 65 objects and 6 meshes each, with their `male_base` (52

confirmation, not just silence: `TransProxy` binding **1 of 47 → 38 of 47**, and
**37 of the newly bound are player anchors** — exactly the 37 unresolved `.tp`

⚠ **Partial, stated plainly:** the characters are **not placed**. All nine sit at

## 2. ⛔ The finding: a faithful iterator, an unfaithful driver

### 2.1 How it was found — an absolute census, chosen because the aggregate could not speak

X4d's parting lesson was to state in advance what a clean run would rule out.
X4d's venue census reported `114 meshes (0 skinned)`, and that number is
consistent with **two** completely different worlds: the crowd never joined the
tree, or it joined the tree and is empty. **No aggregate mesh count, coverage %,
or colour count can separate those.** The instrument that can is a **per-dir
object count** (`--dump-tree`), and it answered in one run:

```
small_club_01                    [WorldDir] objs=2   mesh=0   char=0  sub=1
  …/small_club_01_base.milo      [WorldDir] objs=383 mesh=101 char=1  sub=5   PROXY
    …/world_chars.milo           [RndDir]   objs=46  mesh=0   char=0  sub=1   PROXY
      …/chars.milo               [RndDir]   objs=11  mesh=0   char=8  sub=2   PROXY
        crowd_male01             [Character] objs=65 mesh=6   char=0  sub=1   PROXY
        …  (× 8: crowd_male01..04, crowd_female01..04)
```

`char=8` with `mesh=0` **in the same dir** is the whole story: the eight crowd
members are present as objects, and their meshes are one level further in, inside
each `Character`-as-dir.

### 2.2 The gap

| | walk |
|---|---|
| `ObjDirItr(dir, recurse=true)` | root's hash table, then `mSubDirs` depth-first via `ObjectDir::NextSubDir` (`obj/Dir.h:536`, `:700-760`) |
| what it never enters | the hash table of a **dir-typed object**, i.e. any `Character`, `CharClipSet`, or nested `ObjectDir` **stored as an object rather than as a subdir** |

⚠ **This is NOT a decomp defect, and it must not be "fixed" in `src/`.** Retail
never needs a flat mesh list: it draws through the `RndDrawable` tree, where a
`Character` draws its own contents when its parent draws it. `ObjDirItr` is
faithful and X2 certified it. **It is `rb3-render` that is unfaithful** — it
draws a flat `std::vector<RndMesh*>` (`main_render.cpp`, the `m->DrawShowing()`
loop X4b recorded at its `:1622`), and for *that* consumer the `mSubDirs`-only
walk silently omits an entire subsystem.

Fixed driver-side with `CollectDeep<T>` — the same walk plus a descent into
dir-typed hash-table objects. A `std::set<ObjectDir*>` seen-guard is **load
bearing, not defensive**: `char/crowd/anim/shared_clips.milo` is reachable under
all eight crowd members and several proxies are reachable by more than one path.

**Measured, `small_club_01`:**

| | legacy walk | deep walk |
|---|---|---|
| meshes | 114 | **180** |
| skinned | **0** | **48** (8 crowd × 6) |
| drawn | 96 | **162** |
| with a `Mat` | 113 | 179 |
| with a diffuse `Tex` | 93 | 159 |
| distinct colours | 111930 | 112634 |

⚠ **Coverage stays 38.92% in the wide shot.** That is not a contradiction and it
is worth stating: the eight characters are stacked at the origin of a venue whose
bbox spans ~500 units, so they occupy a few hundred pixels. **The colour count
moved and the coverage did not — which is exactly why coverage was never a
sufficient oracle for this.**

## 3. ⭐ `player0` resolved without `BandCharacter` — and without repeating X4d's refuted bind

### 3.1 The inherited cost estimate, re-derived

X4d handed this off as: *"Player-targeted lighting — 49 + 14 unresolved
`player0..3` refs. **Needs `BandCharacter`** — i.e. the `ScatterIncludes` lane."*
The charter told me to say so if I inherit a cost estimate and to re-measure
before it drives the plan. **I inherited it, I re-measured, and it is wrong** —
not about the facts, but about the required work.

The facts hold up exactly. `player0` **is** a file-resident `BandCharacter`
serialized in `world/shared/chars.milo` (confirmed independently against the
rb3-Wii oracle and the asset's own class/name table), and `BandCharacter` **is**
one of the four factory misses in that file. So the chain X4d described is real.

What does not follow is that resolving the *refs* needs the *class*.

### 3.2 What actually resolves them

`ObjPtr` name resolution already has a native fallback chain
(`obj/ObjPtr_p.h:230-247`): local dir → up the parent dir chain → finally
**`ObjectDir::Main()->FindObject(buf, false)`**. And `main_render.cpp` calls
`DataInit()`, which calls `ObjectDir::PreInit(19997, 150000)` and creates
`Main()`. So an `ObjectDir` **named `player0`, registered in `Main()` before the
venue loads**, is found by the venue's own `.tp`/`.lit` refs as they load. A
`Character` is an `ObjectDir` whose contents are exactly the `bone_*.mesh`
transforms the `.tp`s look up through `mPart`.

`--player-standin <arkPath>` does precisely that and nothing else.

★ **Critically, this does NOT repeat X4d's refuted shortcut.** X4d proved that
binding `BandCamShot` → `CamShot::NewObject` retires the misses and **breaks the
load** (`rc=134`), because a base-class substitute *mis-parses* the derived
payload from the first field and never returns to `ReadDead`:

> **`ReadDead` recovers objects that were SKIPPED. It cannot recover an object
> that was MIS-PARSED, because the parse never returns.**

That principle generalises, and it applies to `BandCharacter` → `Character`
just as hard. **So we do not touch the factory at all.** The four
`BandCharacter` misses stay misses, `ReadDead` still recovers them, and the
stand-in is a *separate object added alongside*. A miss remains strictly better
than a wrong parse; we simply give the danglers something real to point at.

### 3.3 Measured, with a control and a positive signal

```

couldn't find player0        49            0
couldn't find player1         5            5     <-- control: no stand-in supplied
couldn't find player2         5            5     <-- control
couldn't find player3         4            4     <-- control
total couldn't-find          65           16
```

The `player1..3` rows are the control that matters: they rule out "the warning
got suppressed globally" as the explanation for the `player0` row.

★ **And silence is not success, so here is the positive signal.**
`RndTransProxy::Sync()` (`rndobj/TransProxy.cpp:73-90`) calls
`SetTransParent(target)` **only** on a successful resolve of `mProxy` *and* a
successful `Find<RndTransformable>(mPart)` inside it; on failure it explicitly
`SetTransParent(nullptr)`. So a non-null `TransParent()` is a per-object
assertion that the whole anchor chain bound:

| | bound | unbound | of | bound player anchors |
|---|---|---|---|---|
| baseline | **1** | 46 | 47 | **0** |
| + `player0` stand-in | **38** | 9 | 47 | **37** |

**37** newly bound player anchors is exactly the **37 unresolved `.tp` player
refs** X4d reported. The venue's `player_{bass,drum,guitar,vocals}0_*`
transform proxies are now parented into a real character's skeleton, which is
the mechanism `BandWardrobe::SyncTransProxies` implements in retail
(`bandobj/BandWardrobe.cpp:345-359`).

⚠ **Stated plainly — this is a STAND-IN.** It is a `Character`, not the asset's
`BandCharacter`, so its wardrobe / `BandCharDesc` / `MergeFilter` state is ours,
not the asset's. It proves the anchor-and-lighting chain end to end and makes the
venue's own lighting rig aimable. **It does not substitute for landing the real
TU**, and the real TU is still owed.

## 4. Driving the crowd from the clips the venue already ships

X4b/X4c drove one character from an externally supplied `--clips` file. A venue
does not need that: each crowd member already carries
`char/crowd/anim/shared_clips.milo`, whose `male_base` (52 clips) and
`female_base` (56 clips) `CharClipSet`s are resident and already bound to the
right skeleton. `--scene-clip <name>` drives **every** `Character` in the scene
from its own set.

Everything load-bearing from X4b is preserved deliberately: `StuffBones` before
`Play` (without it the driver plays into an empty bone set and the figure stays
in bind pose **while reporting success** — X4b's silent-success failure); the
clock is **stepped**, not jumped, because `CharDriver` blends between poll
instants; `--beat` is relative to `clip->StartBeat()`.

Result: **8 of 9 characters driven**, 41 polls to beat 4.0, `0 no-driver,
1 no-clip, 0 no-servo`. The one skip is `lighttarget`, a `Character` whose bound
set is `lighttarget_clips_base` (`side2side`, `front2back`, `still`,
`circle_counterclockwise`) — it is the venue's light-aiming rig, not a person,
and skipping it is correct.

## 6. ⛔ What did NOT land: placement

All nine characters render at `(0,0,0)`. This is measured, not inferred —
`ReportCharacterPlacement` prints absolute world positions and says
`9 character(s) at 1 DISTINCT world position(s) <== ALL STACKED`. **An aggregate
count or a coverage % would have shown eight correctly scattered characters and
eight stacked ones identically**, which is exactly why the charter asks for
absolute positions.

Two separate mechanisms are missing, and they are not the same problem:

1. **The crowd is not scattered.** `WorldCrowd` places `mNum` characters
   procedurally onto `mPlacementMesh` (`world/Crowd.h:126-131`) and draws them
   through `RndMultiMesh` instancing plus a 3D subset (`Draw3DChars`,
   `m3DChars`). Six `WorldCrowd` objects load in this venue and none runs.
   ★ **Consequence worth naming:** the eight characters in `chars.milo` are
   **archetypes** — `WorldCrowd::CharDef::mChar` is documented *"The character to
   use as the archetype"* (`world/Crowd.h:41-42`). They are the models the crowd
   is instanced *from*, not crowd members at their positions. What renders today
   is eight archetypes at their default transform, which is real shipped
   geometry correctly skinned and driven, but it is **not** "the crowd".
2. **The band is not placed.** Retail places player slots from a venue-resident
   `BandConfiguration`'s stored per-slot / per-play-mode `Transform`, applied
   through a runtime `Waypoint` via `Character::Teleport`
   (rb3-Wii `bandobj/BandConfiguration.cpp:47-56`, `char/Character.cpp:529-538`).
   ⚠ **`BandConfiguration` is not ported in rb3-xenon** — only a factory shim
   exists (`bandobj/Band.cpp:66-73`, and it is one of the 675 misses). So nothing
   will ever call `Teleport`, and a placed band needs that TU (176 lines in the
   oracle) regardless of `BandCharacter`.

I deliberately did **not** invent placement transforms. A hand-picked position
would look better in a screenshot and would be indistinguishable, in the
evidence, from the real thing.

## 7. Retracted hypotheses, with evidence

1. ⛔ **X4d §5: "Skinned characters ⬜ UNREACHED — 0 skinned meshes.
   `BandCharacter` unregistered (4 misses)" and "Crowd ⬜ UNREACHED — `WorldCrowd`
   is registered, but no crowd is instantiated in this root."**
   **Retracted by measurement.** Eight crowd `Character`s were fully resident in
   the venue in X4d's own `rc=0` run — 65 objects and 6 meshes each, with their
   52/56-clip `CharClipSet`s. The `0 skinned` was produced by an iterator that
   cannot enter a dir-typed object's hash table, and the attribution to
   `BandCharacter` was a coincidence: `BandCharacter` really is missing, it just
   was not what emptied the census. **The crowd needed no new class, no factory,
   and no load fix — only a walk that reaches it.** §2.
2. ⛔ **X4d §8: "Player-targeted lighting … Needs `BandCharacter` — i.e. the
   `ScatterIncludes` lane."**
   **Retracted as a cost claim.** Every fact in it is right; the conclusion is
   not. 49 → 0 with **zero** factory changes, **zero** `BandCharacter`, and
   **zero** `ScatterIncludes` work, by registering a real shipped `Character`
   named `player0` in `ObjectDir::Main()` and letting the *existing* native
   fallback (`obj/ObjPtr_p.h:246`) do the resolution. §3.
   ⚠ The complement is **not** retracted: the real `BandCharacter` TU is still
   owed, and the stand-in does not stand in for it.
3. ⛔ **My own first clip-selection rule: "search the character's clip sets for
   the named clip and use the first that has it."**
   **Retracted by its own output.** `shared_clips.milo` carries **both**
   `male_base` and `female_base`, and `crowd_reaching_01` exists only in
   `female_base` — so hash order handed `crowd_male01` a **female clip**. It
   rendered, it reported success, and it was wrong. Replaced by
   `CharDriver::ClipDir()` (the driver-bound set) with **no cross-set fallback**:
   a character whose own set lacks the clip is skipped and says so. This is the
   same silent-success shape X4b warned about, arriving through a new door.
4. ⛔ **My own working hypothesis while reading `ObjectDir::PostLoad`: "the proxy
   `DirLoader` is fire-and-forget and is never polled to completion, so the crowd
   proxy dirs are resident but EMPTY."**
   A clean, plausible mechanism that would have explained `0 skinned` exactly.
   **Retracted before it cost anything, by the census I built to test it:** the
   crowd dirs are not empty, they hold 65 objects each. The one genuinely empty
   proxy in the whole venue is `sfx/audio_mixer.milo` (`objs=0`), which is the
   closed `synth/` gate and expected. **Measuring the state beat reasoning about
   the mechanism** — X4d's §10.2 lesson, and it held.
5. ⚠ **Explicitly NOT claimed:** that the scene is *correct*, or that this is
   what RB3 looks like. There is no retail ground truth in this loop. The claim
   is "the venue's own characters load, are driven by the venue's own clips, and
   render under the venue's own environ." §6 states what is missing, and
   placement is missing.

### 7.1 ⚠ The zsh word-split trap caught a third lane — me

## 10. Recommended X6 shape

1. ★ **When an aggregate can be produced by two different worlds, it is not an
   oracle — it is a coincidence you have not resolved yet.** `114 meshes (0
   skinned)` was equally consistent with "the crowd never loaded" and "the crowd
   loaded and the iterator can't see it", and four milestones read it the first
   way. A per-dir object count separated them in one run. Before trusting a
   number, ask what *else* would produce it.
2. ★ **Re-derive an inherited cost estimate from the mechanism, not from the
   handoff.** "Needs `BandCharacter`, i.e. the `ScatterIncludes` lane" was built
   from entirely correct facts and was still off by a whole build-system lane,
   because nobody had asked what *resolution* actually requires — which turned
   out to be an object with the right name in a dir the existing fallback already
   searches. This is X4d's own §10.4 lesson recurring one milestone later, from
   X4d.
3. ★ **The cheapest correct thing is often "give the danglers something real to
   point at", not "make the missing class exist."** But note what makes that
   legitimate here and *not* legitimate for `BandCamShot`: we added an object
   **alongside** a miss, we never asked a wrong class to **parse** a payload.
   That is the line X4d drew, and it is the line to keep drawing.
4. **Placement is now the whole game.** Geometry, materials, textures, lighting,
   skinning, animation and ref resolution are all alive in one scene. What
   separates this frame from a Rock Band frame is that everyone is standing on
   the same spot — and the two mechanisms that fix it (`WorldCrowd` scatter,
   `BandConfiguration`+`Teleport`) need **neither** `BandCharacter` nor the
   `ScatterIncludes` lane.
