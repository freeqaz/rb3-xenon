## Why (context you need, nothing else assumed)

The msvc ninja rule on main (build.ninja ~lines 41-46, generated by tools/project.py:747-772) is:

```
rule msvc
  command = bash -c 'set -o pipefail; WIBO_FS_CACHE=1 build/tools/wibo
      build/compilers/$mw_version/cl.exe $cflags /showIncludes /Fo$out $in
      | $python tools/transform_dep.py'
  deps = msvc      # msvc_deps_prefix = "Note: including file:"
```

Three problems, one root cause:

1. `build/tools/wibo` is the VANILLA upstream 1.0.1 release (verify yourself:
   `strings build/tools/wibo | grep WIBO_` → no WIBO_FS_CACHE). It got there because
   configure.py (~line 266, inside `if not is_windows():`) does `config.wrapper = args.wrapper`
   with no default, so `use_wibo()` (tools/project.py:274-280) returns True and project.py
   emits a `download_tool` edge (tools/project.py:626-636; visible at build.ninja:24-26,
   tag "1.0.1") that downloads stock wibo — clobbering the fork binary commit 9b938ea assumed.
   So `WIBO_FS_CACHE=1` is a no-op on main: measured 389 ms/TU at 32-wide instead of 25 ms
   (15.6x), ~270 s wasted per full ~745-TU build.
2. The `| $python tools/transform_dep.py` pipe costs ~29 ms/TU. The fork wibo implements the
   identical rewrite in-process behind `WIBO_REWRITE_SHOWINCLUDES=1` (byte-level equivalence +
   ninja `-t deps` positive/negative controls verified by a prior research agent; ninja's own
   CanonicalizePath absorbs the one `..`-collapse divergence and trailing `\r`). dc3-decomp
   runs this exact wibo code path in production.
3. Worktrees ALREADY use the fork binary: scripts/setup_worktree.sh:103 sets
   `WIBO="$TOOL_DIR/wibo/build/release/wibo"` (TOOL_DIR = `/home/free/code/milohax`, line 98)
   and passes `--wrapper "$WIBO"` to configure.py (line ~364-367). Main's relative
   `build/tools/wibo` vs worktrees' absolute path makes the msvc command strings differ →
   every fresh worktree recompiles all ~745 objs once. Making main use the SAME absolute path
   is load-bearing for the wave-3 warm-worktree seeding (W3-B).

DANGER COUPLING: `WIBO_REWRITE_SHOWINCLUDES=1` with a stock binary is silently ignored → raw
backslash/wrong-case Windows paths reach ninja's deps=msvc parser → corrupted dependency
tracking. Therefore the pipe removal and the wrapper fix MUST land in the same commit, and
configure.py must HARD-FAIL if the wrapper binary lacks the feature.

There is also an UNCOMMITTED in-flight diff in configure.py (from an interrupted L2 agent —
read `git diff configure.py` first): it rewrites `_find_local_fork()` (configure.py:~174+) to
prefer prebuilt `<fork>/target/release/<bin>` binaries in BOTH the upward-walk and the
absolute-fallback paths, so bare `python3 configure.py` yields a byte-identical build.ninja in
main and in detached worktrees. That diff is correct and load-bearing — you will keep it,
extend the same philosophy to the wibo wrapper, and commit it as part of this window.
